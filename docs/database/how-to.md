## Изменить модель (добавить поле)

Самый частый случай. Пример: в `Bot` добавляем необязательный комментарий пользователя.

### 1. Правим модель

`backend/src/models/bot.py`:

```python
comment: Mapped[str | None] = mapped_column(String(200), nullable=True)
```

### 2. Генерируем миграцию

```bash
alembic revision --autogenerate -m "add comment to bots"
```

Alembic сравнивает модели с реальной схемой вашей локальной базы и пишет новый файл в
`alembic/versions/`. В выводе видно, что он нашёл:

```
INFO  [alembic.autogenerate.compare] Detected added column 'bots.comment'
```

### 3. Читаем сгенерированный файл глазами

**Этот шаг пропускать нельзя.** Autogenerate — помощник, а не истина: он не понимает
переименований, не всегда видит смену типа и может предложить не то. Открываем
свежий файл в `alembic/versions/` и проверяем, что в `upgrade()` написано ожидаемое:

```python
def upgrade():
    with op.batch_alter_table("bots") as batch_op:
        batch_op.add_column(sa.Column("comment", sa.String(200), nullable=True))
```

Если внутри оказалось что-то лишнее (например, удаление чужой таблицы) — удалите
лишние строки руками или удалите файл целиком и разберитесь, почему база разъехалась
с моделями.

### 4. Применяем локально

```bash
alembic upgrade head
```

### 5. Проверяем

```bash
alembic check      # должно быть: No new upgrade operations detected
python -m pytest   # схема тестов строится из моделей — убедимся, что ничего не сломали
```

### 6. Коммитим модель и миграцию **вместе**

```bash
git add src/models/bot.py alembic/versions/<новый_файл>.py
```

Миграция без модели или модель без миграции — сломанный коммит: у коллеги или на
сервере схема разойдётся с кодом.

---

### Ловушка: новая колонка с `nullable=False`

Если в таблице **уже есть строки**, добавление обязательной колонки без значения по
умолчанию упадёт: СУБД не знает, что записать в существующие строки.

Три рабочих варианта, по возрастанию аккуратности:

**а) Сделать колонку необязательной** (проще всего, если это допустимо):

```python
comment: Mapped[str | None] = mapped_column(String(200), nullable=True)
```

**б) Дать значение по умолчанию на уровне БД** — `server_default` (в отличие от
`default`, он проставляется самой СУБД и применяется к уже существующим строкам):

```python
is_archived: Mapped[bool] = mapped_column(
    Boolean, nullable=False, server_default="false"
)
```

**в) Заполнить в три шага прямо в миграции** — когда осмысленного дефолта нет:

```python
def upgrade():
    # 1. добавляем как необязательную
    op.add_column("bots", sa.Column("owner_label", sa.String(50), nullable=True))
    # 2. заполняем существующие строки
    op.execute("UPDATE bots SET owner_label = 'legacy'")
    # 3. делаем обязательной
    with op.batch_alter_table("bots") as batch_op:
        batch_op.alter_column("owner_label", nullable=False)
```

## Добавить новую таблицу

1. Создайте файл в `backend/src/models/`, например `notification.py`, с классом,
   наследующим `Base`.
2. **Импортируйте модель где-нибудь в коде приложения** — в роутере, сервисе или
   репозитории, который её использует.
3. Дальше — те же шаги 2–6, что и выше (`revision --autogenerate` → прочитать → `upgrade`).

Про пункт 2. Для alembic импорт не нужен: `alembic/env.py` сам обходит папку
`src/models/` и подтягивает все модули. А вот **тестам он нужен**: `conftest.py`
строит схему из `Base.metadata`, наполняемой обычными импортами приложения. Модель, не
импортированная нигде на пути `src.main`, не создастся в тестовой базе и не будет
чиститься между тестами. Если модель ещё нигде не используется, добавьте импорт
явно — иначе о проблеме вы узнаете из непонятного падения теста.

## Удалить или переименовать поле

**Удаление** autogenerate распознаёт корректно — действуйте как в основном рецепте.
Помните только, что откат (`downgrade`) вернёт колонку, но **не данные**: они удаляются
вместе с ней безвозвратно.

**Переименование autogenerate не понимает.** Он видит не «поле переименовали», а
«одно поле исчезло, другое появилось», и сгенерирует `drop_column` + `add_column` —
то есть **потерю всех данных в колонке**. Файл нужно поправить руками:

```python
def upgrade():
    with op.batch_alter_table("bots") as batch_op:
        batch_op.alter_column("comment", new_column_name="user_note")

def downgrade():
    with op.batch_alter_table("bots") as batch_op:
        batch_op.alter_column("user_note", new_column_name="comment")
```

Ровно ради таких случаев в основном рецепте есть шаг «прочитать глазами».

## Первый старт сервиса на сервере

Порядок для чистого сервера. База — SQLite, отдельную СУБД ставить не нужно: это
обычный файл, который создаст сама миграция.

Если сервис на этом сервере **уже работал** и база с таблицами есть — вам нужен другой
рецепт: [подключить alembic к уже работающей базе](#подключить-alembic-к-уже-работающей-базе).

### 1. Ставим зависимости

```bash
cd backend
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
```

Драйвер БД (`aiosqlite`) уже в списке — ничего доустанавливать не нужно.

### 2. Заполняем `.env`

Файл `backend/.env` в `.gitignore`, на сервер он не приезжает — создаётся руками:

```ini
DATABASE_URL=sqlite+aiosqlite:///./cryptobot.db
SECRET_KEY=...
FERNET_KEY=...
SERVICE_COMMISION=0.20
GLITCHTIP_DSN=...
YOOKASSA_SHOP_ID=...
YOOKASSA_SECRET_KEY=...
FRONTEND_URL=https://...
```

Два предупреждения по значениям:

- **`FERNET_KEY` менять нельзя.** Им зашифрованы биржевые ключи пользователей. Другой
  ключ на сервере — и все сохранённые API-ключи превращаются в нечитаемый мусор.
  Если переносите базу с другой машины, переносите и `FERNET_KEY`;
- путь в `DATABASE_URL` **относительный** (`./cryptobot.db`) — файл создастся в той
  папке, из которой запущен процесс. Запустите сервис из другого каталога — получите
  вторую пустую базу и «пропавшие» данные. Надёжнее указать абсолютный путь:
  `sqlite+aiosqlite:////var/lib/botservice/cryptobot.db` (четыре слэша — три от схемы
  плюс корень).

### 3. Создаём схему

```bash
alembic upgrade head
```

Это единственная команда, создающая таблицы, — приложение их больше не создаёт.
Пропустите её, и сервис поднимется, но упадёт на первом же запросе к БД.

### 4. Проверяем

```bash
alembic current    # покажет id миграции и пометку (head)
alembic check      # No new upgrade operations detected
```

### 5. Запускаем сервис

```bash
uvicorn src.main:app --host 0.0.0.0 --port 8000
```

Запускать **одним процессом**: SQLite допускает лишь одну пишущую транзакцию
одновременно, и несколько воркеров uvicorn будут ловить `database is locked`.

## Обновить сервис на сервере

Порядок важен: **миграции накатываются до перезапуска приложения**, чтобы новый код не
успел обратиться к ещё не существующим колонкам.

```bash
cd backend
cp cryptobot.db backups/cryptobot_$(date +%F_%H%M).db   # 1. бэкап
git pull
pip install -r requirements.txt                          # если менялись зависимости
alembic upgrade head                                     # 2. миграции
sudo systemctl restart botservice                        # 3. и только теперь рестарт
```

Если `alembic upgrade head` ничего не написал про применение ревизий — значит новых
миграций в обновлении не было, это нормально. Команда безопасна: повторный запуск на
актуальной базе не делает ничего.

**Про бэкап.** У SQLite это просто копия файла — но копировать его на ходу, при
работающем сервисе, нельзя: можно поймать файл в середине записи. Либо останавливайте
сервис перед копированием, либо снимайте копию штатным средством, которое умеет это
на живой базе:

```bash
sqlite3 cryptobot.db ".backup 'backups/cryptobot_$(date +%F_%H%M).db'"
```

Откат миграции возвращает схему, но не данные (см. про `drop_column` выше). Копия
файла — единственная настоящая страховка.

## Подключить alembic к уже работающей базе

Ситуация: база уже живёт, таблицы созданы старым `Base.metadata.create_all()`, а
истории миграций в ней нет. Накатывать `upgrade head` **нельзя** — первая миграция
попытается создать таблицы, которые уже есть, и упадёт.

```bash
alembic check       # 1. посмотреть, совпадает ли реальная схема с моделями
alembic stamp head  # 2. пометить базу как уже находящуюся на последней миграции
alembic current     # 3. убедиться, что отметка встала
```

`stamp` не выполняет никакого SQL по схеме — он только записывает в служебную таблицу
`alembic_version`: «эта база соответствует такой-то ревизии». Дальше всё идёт обычным
порядком.

Если на шаге 1 `alembic check` покажет расхождения — разберитесь с ними **до** `stamp`.
Иначе вы зафиксируете как «правильное» то состояние, которое правильным не является.
Типичные находки: таблица, которой нет в базе (её создаст `create_all` при разовом
запуске или добавьте отдельную миграцию), и лишняя таблица, которой нет в моделях
(см. следующий рецепт).

## Переезд на PostgreSQL

Пока не сделан — здесь план на случай, когда решитесь. Хорошая новость: миграции
переписывать не придётся, они написаны средствами alembic, а не голым SQL. Основная
работа — **не схема, а данные и то, что на Postgres начнёт проверяться строже**.

### Что нужно сделать

**1. Поставить драйвер.** В `requirements.txt` его нет:

```bash
pip install asyncpg
pip freeze > requirements.txt   # requirements.txt здесь генерируется через freeze
```

**2. Поднять базу:**

```bash
sudo -u postgres psql
```
```sql
CREATE DATABASE botservice;
CREATE USER botservice WITH PASSWORD 'ваш_пароль';
GRANT ALL PRIVILEGES ON DATABASE botservice TO botservice;
\c botservice
GRANT ALL ON SCHEMA public TO botservice;   -- нужно на PostgreSQL 15+
\q
```

**3. Поменять `DATABASE_URL`** в `.env`:

```ini
DATABASE_URL=postgresql+asyncpg://botservice:ваш_пароль@localhost:5432/botservice
```

Префикс `postgresql+asyncpg://` обязателен: обычный `postgresql://` подхватит
синхронный psycopg2 и приложение не стартует (см. таблицу отладки).

**4. Создать схему:**

```bash
alembic upgrade head
```

**5. Перелить данные.** Alembic создаёт **пустые** таблицы — содержимое старой базы
он не переносит, это не его работа. Данных немного и таблиц шесть, так что достаточно
разового скрипта: читать из SQLite и вставлять в Postgres, соблюдая порядок
(`users` → `exchange_api_keys` → `bots` → `trades` → `payments` →
`balance_transactions`), иначе упрётесь во внешние ключи. Готовые конвертеры
(`pgloader`) тоже подойдут, но на шести таблицах скрипт предсказуемее.

**6. Проверить и запустить:**

```bash
alembic check      # схема совпадает с моделями
python -m pytest   # тесты гоняются на своей SQLite, но пусть будут зелёные
```

### К чему готовиться

**Внешние ключи включатся.** На SQLite они не проверялись, поэтому в базе могут быть
«сироты» — строки, ссылающиеся на удалённого пользователя или бота. При переливке они
дадут ошибку внешнего ключа. Найдите их **до** переезда:

```sql
SELECT COUNT(*) FROM bots   WHERE user_id NOT IN (SELECT id FROM users);
SELECT COUNT(*) FROM trades WHERE user_id NOT IN (SELECT id FROM users);
SELECT COUNT(*) FROM trades WHERE bot_id  NOT IN (SELECT id FROM bots);
```

Ненулевые числа — это данные, которые надо либо удалить, либо привязать заново.

**Типы станут строже.** SQLite к типам относится вольно (в колонку `Float` можно
положить строку), Postgres — нет. Если в базе накопилось что-то не того типа,
всплывёт это именно при переливке.

**Даты.** Все `created_at` объявлены как `DateTime(timezone=True)`, но SQLite таймзону
физически не хранит. При переносе явно указывайте, что сохранённые значения — UTC,
иначе получите сдвиг.

**Бэкап и рестарт.** Обратно на SQLite вы не откатитесь одним движением, поэтому
сохраните файл `cryptobot.db` до начала и не удаляйте его ещё какое-то время после.

## Откатить миграцию

```bash
alembic downgrade -1          # на одну назад
alembic downgrade <revision>  # к конкретной ревизии
alembic downgrade base        # к пустой базе (снесёт все таблицы!)
```

Помните: откат возвращает **структуру**, а не данные. Откат миграции, добавлявшей
колонку, удалит эту колонку вместе со всем, что в ней успело накопиться.

На сервере предпочтительнее не откатывать, а выпустить новую миграцию, исправляющую
проблему: так история остаётся линейной и одинаковой на всех окружениях.

## Посмотреть состояние базы

```bash
alembic current     # на какой ревизии эта база
alembic heads       # какая ревизия последняя в коде
alembic history     # вся цепочка миграций
alembic history -v  # то же, подробно
alembic check       # совпадают ли модели с реальной схемой
```

`current` и `heads` показывают разное: первое — про **базу**, второе — про **код**.
Если они не совпали, значит на этой базе не накачены миграции: `alembic upgrade head`.

## Начать локальную базу с нуля

Быстрее и честнее, чем чинить разъехавшуюся локальную SQLite-базу. Данные, разумеется,
теряются — на локальной машине это обычно не жалко.

```bash
rm cryptobot.db
alembic upgrade head
```

Проверить: `alembic current` покажет последнюю ревизию, `alembic check` — отсутствие
расхождений.

## Убрать таблицу feedbacks

В локальных базах осталась таблица `feedbacks` от удалённой фичи. Модели под неё нет,
поэтому `alembic check` постоянно предлагает её удалить.

Самый простой путь для локальной базы — [пересоздать её с нуля](#начать-локальную-базу-с-нуля):
в миграциях `feedbacks` нет, поэтому свежая база будет чистой.

Если таблица есть и на сервере и её нужно убрать аккуратно, сначала **проверьте, не
нужны ли данные** (там лежат обращения пользователей), сохраните их, а затем создайте
миграцию:

```bash
alembic revision -m "drop legacy feedbacks table"
```

и впишите в неё руками:

```python
def upgrade():
    op.drop_table("feedbacks")

def downgrade():
    pass  # восстановить нечем: модели нет, структура утеряна
```

## Отладка: симптом → причина

| Симптом | Причина и что делать |
|---|---|
| `no such table: bots` | На этой базе не накачены миграции: `alembic upgrade head` |
| База «пустая», хотя данные были | Относительный путь в `DATABASE_URL` (`./cryptobot.db`): сервис запустили из другого каталога и он создал вторую базу. Ищите лишний `cryptobot.db` или пропишите абсолютный путь |
| `database is locked` | SQLite пускает только одну пишущую транзакцию. Работают два процесса (например, несколько воркеров uvicorn или скрипт параллельно с сервисом) — оставьте один |
| `no such column: bots.comment` | Модель поменяли, миграцию не сгенерировали или не применили. `alembic check` покажет расхождение |
| `Target database is not up to date` (при `revision --autogenerate`) | На локальной базе есть непринятые миграции. Сначала `alembic upgrade head`, потом генерируйте новую |
| `Can't locate revision identified by '...'` | В `alembic_version` записана ревизия, файла которой нет в `alembic/versions/` (например, откатили ветку с миграцией). Вернуть файл или `alembic stamp <существующая_ревизия>` |
| `Multiple head revisions are present` | Две миграции с одинаковым `down_revision` — обычно после слияния веток. Объединить: `alembic merge heads -m "merge"` |
| Autogenerate создал **пустую** миграцию | Alembic не увидел изменений: модели совпадают с базой. Либо вы уже применили миграцию, либо файл модели не в `src/models/` |
| Autogenerate предлагает удалить чужие таблицы | В базе есть таблицы без моделей (как `feedbacks`). Уберите лишние операции из файла миграции руками |
| Миграция применилась локально, но упала на сервере | Почти всегда `nullable=False` на непустой таблице: локально таблица пустая, на сервере — нет. См. [ловушку выше](#ловушка-новая-колонка-с-nullablefalse) |
| Тесты зелёные, а на сервере `no such column` | Тесты строят схему из моделей и про миграции ничего не знают. Проверяйте `alembic check`, а не только pytest |
| Удалили пользователя, а его боты/сделки остались | Так и есть: SQLite не проверяет внешние ключи, `ondelete="CASCADE"` не срабатывает. Чистить связанные строки должен код. См. [README](README.md#внимание-сейчас-ничего-из-этой-таблицы-не-работает) |

Появится при переезде на Postgres:

| Симптом | Причина и что делать |
|---|---|
| `InvalidRequestError: The asyncio extension requires an async driver to be used. The loaded 'psycopg2' is not async` | В `DATABASE_URL` указан `postgresql://` или `postgresql+psycopg2://`. Нужен `postgresql+asyncpg://` |
| `ModuleNotFoundError: No module named 'asyncpg'` | Драйвер не установлен: `pip install asyncpg` |
| `relation "bots" does not exist` | Миграции не накачены на эту базу: `alembic upgrade head` |
| `ForeignKeyViolation` при переливке данных | В старой SQLite-базе есть «сироты» — Postgres их не принимает. Найдите и почистите, запросы в [рецепте переезда](#переезд-на-postgresql) |

## Чек-листы

### Перед коммитом, если трогали модели

- [ ] `alembic revision --autogenerate -m "..."` — миграция сгенерирована
- [ ] Файл миграции **прочитан глазами**, лишнего в нём нет
- [ ] `alembic upgrade head` — применяется без ошибок
- [ ] `alembic check` — расхождений нет
- [ ] `python -m pytest` — 72 теста зелёные
- [ ] Модель и миграция попали в **один коммит**

### Перед деплоем на сервер

- [ ] Сделана копия боевой базы (`sqlite3 cryptobot.db ".backup ..."` либо копия файла
      при остановленном сервисе)
- [ ] Порядок соблюдён: `git pull` → `alembic upgrade head` → перезапуск сервиса
- [ ] После деплоя: `alembic current` показывает последнюю ревизию
- [ ] Если добавлялась обязательная колонка — проверено, что у неё есть
      `server_default` или заполнение в миграции
