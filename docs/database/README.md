## Коротко: три команды, которые нужно помнить

Все команды — из папки `backend/`.

```bash
alembic upgrade head     # привести БД к актуальной схеме (после clone/pull/деплоя)
alembic current          # на какой миграции сейчас эта БД
alembic check            # совпадают ли модели в коде с реальной схемой БД
```

Четвёртая команда нужна, только когда вы **сами поменяли модель**:

```bash
alembic revision --autogenerate -m "что поменяли"
```

Всё остальное — детали, за которыми можно вернуться сюда позже.

## Что где лежит

```
backend/
├── .env                          # DATABASE_URL — строка подключения (в .gitignore)
├── alembic.ini                   # конфиг alembic (URL внутри — заглушка, см. ниже)
├── alembic/
│   ├── env.py                    # ЕДИНСТВЕННЫЙ файл alembic, который мы правили руками
│   ├── script.py.mako            # шаблон новых миграций, трогать не нужно
│   └── versions/                 # сами миграции, по файлу на изменение схемы
│       └── 0ad8eafc7bcb_initial_schema.py
├── cryptobot.db                  # локальная SQLite-база (в .gitignore)
└── src/
    ├── database.py               # engine, фабрика сессий, Base, зависимость get_db
    ├── models/                   # ORM-модели = описание таблиц (источник правды)
    └── repositories/             # запросы к таблицам, чтобы SQL не растекался по сервисам
```

**Источник правды по схеме — `src/models/`.** Миграции в `alembic/versions/` — это
история того, как схема к текущему виду пришла; они генерируются из моделей, а не
пишутся руками.

## Какая это вообще база

**Сейчас везде SQLite** — и на машине разработчика, и в тестах, и на сервере.

| Где | СУБД | Строка подключения |
|---|---|---|
| Локальная разработка | SQLite, файл `backend/cryptobot.db` | `sqlite+aiosqlite:///./cryptobot.db` |
| Тесты | SQLite, файл `backend/test.db` (пересоздаётся) | задаётся в `tests/conftest.py` |
| Сервер | SQLite, файл рядом с приложением | `sqlite+aiosqlite:///./cryptobot.db` |

СУБД задаётся одной строкой `DATABASE_URL` в `backend/.env` — больше нигде она не
зашита. Alembic берёт эту же строку, так что приложение и миграции всегда смотрят в
одну базу.

Проект работает с БД **асинхронно** (`create_async_engine` в
[database.py](../../backend/src/database.py)), поэтому драйвер тоже обязан быть
асинхронным: для SQLite это `aiosqlite`, он стоит в `requirements.txt` — ничего
доустанавливать не нужно.

### Про переход на PostgreSQL

Переезд обсуждается, но пока не сделан. Миграции к нему готовы: они написаны
средствами alembic, а не голым SQL, поэтому на Postgres встанут без переписывания.
Что реально понадобится сделать — собрано в отдельном рецепте:
[переезд на PostgreSQL](how-to.md#переезд-на-postgresql). Коротко: поставить драйвер
`asyncpg` (в `requirements.txt` его нет), поменять `DATABASE_URL` и **перелить данные** —
alembic создаст пустые таблицы, но содержимое старой базы не перенесёт.

Пока переезда нет, помните про два ограничения SQLite, описанные ниже: **внешние ключи
не проверяются** и **параллельная запись сериализуется**.

## Схема: таблицы и связи

Шесть таблиц. В центре — `users`, всё остальное принадлежит пользователю.

```
users
 ├──< exchange_api_keys      ключи от биржи (шифрованные)
 │      └──< bots            бот может ссылаться на ключ (или работать в dry_run без него)
 ├──< bots                   настройки и состояние торгового бота
 │      └──< trades          сделки, вычитанные из freqtrade
 ├──< trades                 (денормализованная ссылка: сделка знает и бота, и владельца)
 ├──< payments               пополнения баланса через ЮKassa
 └──< balance_transactions   журнал движений баланса (модель есть, код её НЕ пишет)
             └──> trades     необязательная ссылка на сделку, за которую списана комиссия
```

В моделях у связей проставлено поведение при удалении родителя:

| Связь | `ondelete` | Что задумано |
|---|---|---|
| `bots.user_id` → users | `CASCADE` | удалили пользователя — его боты удалились |
| `trades.user_id` / `trades.bot_id` | `CASCADE` | то же для сделок |
| `exchange_api_keys.user_id` | `CASCADE` | то же для ключей |
| `balance_transactions.user_id` | `CASCADE` | то же для транзакций |
| `bots.api_key_id` → exchange_api_keys | `SET NULL` | удалили ключ — бот остался, ключ обнулился |
| `balance_transactions.trade_id` → trades | `SET NULL` | удалили сделку — запись в журнале осталась |
| `payments.user_id` → users | **не задан** | удаление пользователя с платежами упёрлось бы в внешний ключ |

### Внимание: сейчас ничего из этой таблицы не работает

SQLite не проверяет внешние ключи, пока не включён `PRAGMA foreign_keys` — а он
выключен (`PRAGMA foreign_keys = 0`), и мы его нигде не включаем. Проверено на живой
базе: удаление пользователя оставляет его ботов на месте.

```
Удалили пользователя. Ботов осталось: 1   (при работающем CASCADE было бы 0)
```

То есть **`CASCADE` и `SET NULL` сейчас не срабатывают ни локально, ни на сервере** —
база везде SQLite. Удаление родительской строки молча оставляет висящие ссылки на
несуществующего владельца, а `payments` не защищает пользователя от удаления.

Практические следствия:

- нельзя рассчитывать, что удаление пользователя вычистит его данные — за этим должен
  следить код, а не БД;
- «сироты» в базе возможны, и запрос с `JOIN` их просто не увидит, а `WHERE user_id = ...`
  вернёт;
- на Postgres всё это **включится само** и то, что раньше молча проходило, начнёт
  падать с ошибкой внешнего ключа. Это одна из причин прибраться в данных до переезда.

Включить проверку на SQLite можно обработчиком `connect` на движке (`PRAGMA
foreign_keys=ON`), но это отдельное решение с последствиями для существующих данных —
сначала стоит убедиться, что сирот в базе нет.

## Таблицы по одной

Полный список колонок всегда актуален в `src/models/` — здесь только назначение и то,
что не читается из кода само собой.

### `users` — [user.py](../../backend/src/models/user.py)

Аккаунт. Помимо email/пароля хранит **денежную часть**:

- `service_balance` — внутренний баланс в рублях, с него списывается комиссия сервиса.
  Меняется прямым `UPDATE` в `commission_service` и `payment_service`;
- `commission_rate` — доля прибыли, которую берёт сервис (`0.20` = 20%), по умолчанию
  из `SERVICE_COMMISION` в `.env`. Хранится у каждого пользователя отдельно, чтобы
  можно было дать кому-то индивидуальные условия, не трогая остальных;
- `is_active` — блокировка аккаунта.

### `exchange_api_keys` — [exchange_api_key.py](../../backend/src/models/exchange_api_key.py)

Ключи от биржи. `api_key_encrypted` / `api_secret_encrypted` шифруются через **Fernet**
(ключ `FERNET_KEY` из `.env`) перед записью и расшифровываются при чтении.

В БД лежит **шифротекст**. Потеряете `FERNET_KEY` — расшифровать ключи будет нечем,
их придётся заводить заново; смена `FERNET_KEY` на сервере ломает все уже сохранённые
ключи. Резервная копия базы без `FERNET_KEY` бесполезна в этой части.

### `bots` — [bot.py](../../backend/src/models/bot.py)

Самая широкая таблица: и пользовательские настройки, и служебное состояние.

- **PK — строка**, а не число: UUID (`String(36)`). Этот же id используется как имя
  папки бота и имя Docker-контейнера, поэтому он строковый;
- `entry_filters_long`, `entry_filters_short`, `take_profit`, `trailing_config` —
  колонки типа **JSON**. `take_profit` хранится сразу в формате `minimal_roi`
  freqtrade (`{"0": 0.04}`), чтобы при генерации конфига ничего не переводить;
- `stop_loss` — если пользователь выключил стоп-лосс, пишется `-0.99`, то есть
  «фактически выключен». Отдельного флага нет;
- `status` — `created` / `starting` / `running` / `stopped` / `error`. По нему
  `polling_worker` выбирает, кого опрашивать (`status == "running"`);
- `container_id`, `api_port`, `api_username`, `api_password` — как достучаться до
  freqtrade-контейнера этого бота. Пароль лежит **в открытом виде** (в отличие от
  биржевых ключей): это доступ к локальному контейнеру, не к деньгам;
- `is_active` — «мягкое удаление»: бот архивирован, но строка осталась ради истории сделок;
- `total_profit`, `total_commission_paid_usdt/rub` — накопительные счётчики.

### `trades` — [trade.py](../../backend/src/models/trade.py)

Сделки, вычитанные из freqtrade. Бэкенд их не создаёт сам — их приносит
`polling_worker` раз в 30 секунд.

- `freqtrade_trade_id` — id сделки **внутри контейнера бота**. Это ключ дедупликации:
  воркер по нему понимает, новая это сделка или уже известная. Без него каждый цикл
  опроса плодил бы дубли;
- `close_rate`, `close_time`, `profit_usdt`, `profit_pct` — `NULL`, пока сделка открыта;
- `commission_paid` — **единственная защита от повторного списания денег.** Пока
  флаг `False`, комиссия считается неудержанной. Поведение зафиксировано тестами,
  см. `docs/testing/README.md`;
- `exchange_rate_rub_usdt` — курс на момент закрытия, сохраняется, чтобы потом можно
  было объяснить пользователю, откуда взялась сумма комиссии в рублях.

### `payments` — [payment.py](../../backend/src/models/payment.py)

Пополнения через ЮKassa. **PK — идентификатор платежа от ЮKassa** (строка), а не наш
автоинкремент: так вебхук находит платёж по тому же id, который прислал провайдер.
`status`: `pending` / `succeeded` / `canceled`.

### `balance_transactions` — [balance_transaction.py](../../backend/src/models/balance_transaction.py)

Задумывался как журнал движений баланса (`deposit` / `commission` / `refund`).

**Модель существует, но код в неё ничего не пишет.** Баланс меняется прямым обновлением
`users.service_balance`, аудита движений денег сейчас нет. Таблица создаётся пустой.
Если понадобится разбирательство «откуда списалось» — данных для него в базе нет,
только логи.

## Как код ходит в базу

Три слоя, снизу вверх:

**1. `database.py`** — движок, фабрика сессий и зависимость `get_db`:

```python
async def get_db():
    async with AsyncSessionLocal() as session:
        try:
            yield session
            await session.commit()      # ← коммит автоматический
        except:
            await session.rollback()
            raise
```

Неочевидное следствие: **в ручках не нужно вызывать `commit()` вручную** — если
обработчик отработал без исключения, изменения сохранятся сами. И наоборот: любое
исключение откатывает всё, что ручка успела наделать.

**2. `repositories/`** — по файлу на таблицу (`bot_repository.py`, `trade_repository.py`,
`user_repository.py`, `api_keys_repository.py`, `payments_repository.py`). Здесь живут
сами запросы. Смысл слоя в том, что сервисы получают репозиторий в конструктор — и в
тестах его можно подменить фейком, не поднимая БД вообще.

**3. `services/`** — бизнес-логика, работает через репозитории.

Новый запрос к таблице пишите в репозиторий, а не в сервис или ручку — иначе он не
переиспользуется и его нечем подменить в тестах.

## Alembic: как он здесь настроен

Alembic — это инструмент миграций: он умеет не только создавать таблицы с нуля, но и
менять уже существующие (`ALTER TABLE`), не теряя данные, и хранит историю изменений,
которую можно откатывать.

Раньше схема создавалась вызовом `Base.metadata.create_all()` при старте приложения.
Он умеет ровно одно: создать таблицу, если её ещё нет. Добавленную в модель колонку он
на живой базе **не создаёт и не сообщает об этом** — приложение просто падает при
первом обращении к новому полю. Поэтому `create_all()` из `lifespan()` убран,
за схему теперь отвечает только alembic.

### Что настроено вручную в `alembic/env.py`

Стандартный шаблон alembic для этого проекта не подходил, поэтому в `env.py` три
осмысленные правки — их стоит знать, чтобы не сломать:

**1. URL берётся из `.env`, а не из `alembic.ini`:**

```python
config.set_main_option("sqlalchemy.url", settings.DATABASE_URL)
```

Значение `sqlalchemy.url` внутри `alembic.ini` — заглушка, оставшаяся от генератора;
менять её бессмысленно, она перезаписывается. Приложение и миграции всегда смотрят в
одну и ту же базу — расхождение здесь было бы источником очень неприятных ошибок.

**2. Модели импортируются автоматически:**

```python
for _module_info in pkgutil.iter_modules(src.models.__path__):
    importlib.import_module(f"src.models.{_module_info.name}")
```

Модель попадает в `Base.metadata` только если её модуль импортирован. Список имён
здесь был бы миной: забыли дописать — и autogenerate **молча** пропускает таблицу, без
единой ошибки. Так в этом проекте уже терялась `balance_transactions`: модель была в
коде, а таблицы в базе не было. Теперь новую модель достаточно положить в
`src/models/` — в `env.py` дописывать ничего не нужно.

**3. Batch-режим для миграций:**

```python
context.configure(..., render_as_batch=True)
```

SQLite не умеет полноценный `ALTER TABLE` — в нём нельзя удалить колонку или поменять
её тип. Batch-режим обходит это: alembic создаёт временную таблицу нужной формы,
переливает данные и подменяет старую. Поскольку сейчас база везде SQLite, **без этой
опции половина миграций просто не работала бы**. Если позже переедете на Postgres,
опцию можно оставить — там она не используется и ничему не мешает.

### Как выглядит миграция

Файл в `alembic/versions/` с двумя функциями и ссылкой на предыдущую миграцию:

```python
revision = "0ad8eafc7bcb"       # id этой миграции
down_revision = None            # предыдущая (None = самая первая)

def upgrade():                  # что сделать при накатывании
    op.add_column("bots", sa.Column("comment", sa.String(200), nullable=True))

def downgrade():                # как откатить обратно
    op.drop_column("bots", "comment")
```

Из этих `down_revision` собирается цепочка: alembic всегда знает, в каком порядке
применять миграции и до какой откатывать. Текущее положение конкретной базы хранится
в служебной таблице `alembic_version` внутри самой базы — поэтому каждая база
(локальная, серверная) знает про себя сама.

Сейчас миграция одна — `0ad8eafc7bcb_initial_schema`, создающая все шесть таблиц с нуля.

## Тесты и БД

Тесты **не используют alembic**. `tests/conftest.py` поднимает отдельную SQLite-базу
(`backend/test.db`) и строит схему напрямую из `Base.metadata.create_all()`, а после
прогона сносит.

Это сделано осознанно: тестам нужна схема «как в моделях прямо сейчас», а не история
её изменений, и гонять миграции перед каждым запуском — лишние секунды.

Практическое следствие, о котором надо помнить: **зелёные тесты не доказывают, что
миграция написана правильно.** Тесты возьмут схему из моделей и пройдут, даже если
файл миграции вы забыли сгенерировать. Проверяет это `alembic check`, а не pytest.

Подробнее про тестовую обвязку — в [docs/testing/README.md](../testing/README.md).

## Особенности и ловушки

Честный список того, обо что тут можно споткнуться.

**1. Внешние ключи не работают.** Ни локально, ни на сервере — база везде SQLite,
`PRAGMA foreign_keys` выключен. `CASCADE` и `SET NULL` из моделей не срабатывают,
сироты возможны. Подробно и с проверкой — [выше](#внимание-сейчас-ничего-из-этой-таблицы-не-работает).

**2. SQLite сериализует запись.** Пишущая транзакция в один момент времени может быть
только одна, остальные ждут и по таймауту получают `database is locked`. Бэкенд —
один процесс с одним `polling_worker`, поэтому сейчас это не проблема; станет ею при
втором процессе (второй uvicorn-воркер, скрипт-обслуживание параллельно с сервисом).
Это же — главный технический аргумент за переезд на Postgres.

**3. `asyncpg` нет в `requirements.txt`** — понадобится только при переезде на
Postgres. Лежащий там `psycopg2-binary` синхронный и с `create_async_engine`
несовместим; на SQLite он просто не используется. См.
[рецепт переезда](how-to.md#переезд-на-postgresql).

**4. `bots.total_profit` и сумма `trades.profit_usdt` — два независимых счётчика.**
Их никто не сверяет, и они могут разойтись: `total_profit` досчитывается при обработке
сделки, а от повторной обработки защищён только флаг `trades.commission_paid`
(он охраняет деньги, но не счётчик). Расхождение — известное поведение, не баг,
который надо срочно чинить, но и не то, на что можно опираться в отчётности.

**5. Журнала движений баланса нет.** `balance_transactions` не заполняется, см. выше.

**6. В базе есть «осиротевшая» таблица `feedbacks`.** Модели под неё в коде нет —
похоже, фича была удалена, а таблица осталась. Из-за неё `alembic check` на локальной
базе всегда сообщает `Detected removed table 'feedbacks'`. Это ожидаемо; как убрать
по-хорошему — в [how-to.md](how-to.md#убрать-таблицу-feedbacks).

**7. Время хранится с таймзоной, дефолт проставляется в Python.** Все `created_at`
объявлены как `DateTime(timezone=True)` с `default=lambda: datetime.now(timezone.utc)`.
Значение вычисляет Python при вставке, а не БД, — то есть `INSERT` мимо ORM (руками
через `sqlite3`) значение по умолчанию не получит. Плюс SQLite физически не хранит
таймзону — это всплывёт при возможном переезде на Postgres.

**8. Резервных копий и ретеншена нет.** Ни автоматического бэкапа базы, ни процедуры
восстановления в проекте не описано. Для SQLite это особенно дёшево завести — база
это один файл, — и особенно обидно не иметь: миграции защищают от разъезда схемы,
но не от потери данных.
