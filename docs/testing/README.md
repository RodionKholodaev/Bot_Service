## Быстрый старт

Все команды — из папки `backend/`.

```bash
pip install -r requirements.txt

python -m pytest                      # весь набор, ~5 секунд
python -m pytest -v                   # с именами тестов
python -m pytest tests/unit           # только юниты
python -m pytest tests/unit/test_stats_service.py            # один файл
python -m pytest tests/unit/test_stats_service.py::test_max_drawdown_calculates_percent_from_peak
python -m pytest -k commission        # всё, где в имени есть "commission"
python -m pytest -x --tb=short        # остановиться на первом падении, короткий трейсбек
```

Настройки лежат в `backend/pytest.ini`:

```ini
testpaths = tests      # где искать тесты
pythonpath = .         # чтобы работал импорт `from src...`
asyncio_mode = auto    # async-тесты не требуют декоратора
```

`asyncio_mode = auto` означает, что `@pytest.mark.asyncio` не обязателен — pytest сам
поймёт, что корутину надо выполнить. В проекте декоратор всё равно ставят: так по
сигнатуре сразу видно, что тест асинхронный. **Держитесь этого соглашения.**

CI есть — тесты прогоняются на каждый push в любую ветку

## Что здесь вообще тестируется

Ключевая особенность проекта: **боты — это не код в этом репозитории**. Каждый бот
живёт отдельным Docker-контейнером с freqtrade, и бэкенд общается с ним по HTTP.
Тестнета у нас нет, поднимать реальный контейнер в тестах — долго и хрупко.

Отсюда граница: **тестируется только наш бэкенд**, и всё внешнее подменяется:

| Внешнее | Чем подменяется | Где |
|---|---|---|
| REST API бота (freqtrade) | `FakeApiClient` | `tests/unit/test_polling_worker.py` |
| Docker SDK | `monkeypatch` на `docker_manager` | фикстура `stopped_containers` |
| Курс USDT/RUB (сеть) | `FakeExchangeRateService` | тесты комиссии и синхронизации |
| PostgreSQL | fake-репозитории или SQLite | см. ниже |
| Модель ИИ (AITunnel) | вызова нет — тестируется чистая функция валидации | `test_assistant_suggestions.py` |

Ничего из этого не ходит в сеть. Набор целиком проходит примерно за 5 секунд —
это осознанное свойство, его стоит беречь.

## Структура

```
backend/tests/
├── conftest.py                        # общая обвязка: тестовая БД, http-клиент, очистка
├── fakes/
│   └── test_user_repository.py        # FakeUserRepository — репозиторий в памяти
├── integration/
│   └── test_auth.py                   # HTTP-тесты ручек /auth через реальное приложение
└── unit/
    ├── test_assistant_suggestions.py  # валидация предложений ИИ-ассистента
    ├── test_auth_service.py           # регистрация и вход
    ├── test_comission_service.py      # расчёт и списание комиссии сервиса
    ├── test_polling_worker.py         # живость ботов + синхронизация сделок
    └── test_stats_service.py          # P&L, просадка, winrate
```

Два замечания по именам, чтобы не искать глазами:

- `fakes/test_user_repository.py` — **не тест**, несмотря на префикс `test_`. Это
  переиспользуемый фейк. Префикс достался исторически; pytest пытается собрать оттуда
  тесты, не находит их и идёт дальше.
- `test_comission_service.py` — опечатка в имени файла (одна `m`). Сам сервис называется
  правильно: `src/services/commission_service.py`.

## Два слоя тестов

### Юнит-тесты (`tests/unit/`) — основной слой

Проверяют один сервис, БД не поднимают вообще. Зависимости передаются в конструктор
или подменяются через `monkeypatch`. Быстрые, точные: если такой тест упал, понятно,
какая именно функция сломалась.

**Сюда пишется почти всё новое.**

### Интеграционные тесты (`tests/integration/`) — тонкий слой

Гоняют настоящее FastAPI-приложение через `httpx.AsyncClient(ASGITransport)` — HTTP-запрос
идёт прямо в приложение, без сокетов и без запущенного uvicorn. Работают с настоящей
SQLite-базой (`backend/test.db`, в `.gitignore`).

Их задача — проверить сборку целиком: роутинг, схемы Pydantic, зависимости, коды
ответов, маппинг доменных исключений в JSON. Бизнес-логику здесь дублировать не надо —
её ловят юниты.

Про `lifespan` (важно): `ASGITransport` **не выполняет** startup/shutdown приложения.
Поэтому в тестах не запускается `polling_worker` и не трогается боевая БД.
На это можно опираться, но не стоит забывать — код внутри `lifespan()` не покрыт ничем.

## conftest.py — общая обвязка

Файл применяется ко всем тестам, включая юниты. Что он делает по порядку:

**1. Гасит Sentry.** `src.main` при импорте поднимает `sentry_sdk` с боевым DSN.
Любой `logger.critical` из тестов улетал бы в Glitchtip как настоящий инцидент —
а такие тесты у нас есть (`test_failure_alert_carries_last_ping_error`). Пустой DSN
делает клиент no-op:

```python
sentry_sdk.init(dsn="")
```

Отсюда — неочевидное правило: **импорт `src.main` должен идти после этой строки**.

**2. Поднимает тестовую БД** — SQLite через `aiosqlite`, файл `./test.db`.

**3. Подменяет зависимость `get_db`:**

```python
app.dependency_overrides[get_db] = override_get_db
```

Теперь все ручки приложения работают с тестовой сессией.

**4. Фикстуры:**

| Фикстура | Scope | autouse | Что делает |
|---|---|---|---|
| `prepare_database` | session | да | Создаёт таблицы перед всеми тестами, сносит после |
| `clear_database` | function | да | Чистит все таблицы перед каждым тестом |
| `client` | function | нет | `AsyncClient`, бьющий прямо в приложение |
| `db_session` | function | нет | Сессия к тестовой БД для подготовки данных руками |

`clear_database` идёт по `Base.metadata.sorted_tables` в обратном порядке
(`trades` → `bots` → `payments` → `exchange_api_keys` → `users`) — от зависимых к
родительским, иначе удаление упёрлось бы во внешние ключи. Новая модель начнёт
чиститься сама, править фикстуру не нужно.

Благодаря `clear_database` тесты **не зависят от порядка запуска**: каждый видит
пустую базу. Это то, ради чего фикстура существует, — не ломайте её.

## Паттерны, принятые в проекте

Держитесь их: единый стиль важнее личных предпочтений, потому что читать эти тесты
будут дольше, чем писать.

### 1. Arrange / Act / Assert с явными комментариями

```python
@pytest.mark.asyncio
async def test_zero_profit_trade_charges_no_commission(set_usdt_rate):
    # Arrange
    trade = make_trade(profit_usdt=0.0)
    user = make_user()
    bot = make_bot()
    set_usdt_rate(90.0)

    # Act
    await CommissionService.process_commission(trade, user, bot)

    # Assert
    assert trade.commission_paid is False
    assert user.service_balance == 5000.0
```

Если Act — одна строка и всё очевидно, `# Act`/`# Assert` можно слить в `# Act / Assert`
(так сделано в тестах, проверяющих выброс исключения).

### 2. Фабрики вместо копипасты

У моделей много обязательных полей, а тесту важны два-три. Поэтому в каждом файле
наверху лежат `make_trade` / `make_bot` / `make_user` с разумными дефолтами и
keyword-only аргументами:

```python
def make_trade(*, profit_usdt, commission_paid=False, freqtrade_trade_id=1) -> Trade:
    ...

def make_bot(**overrides) -> Bot:
    defaults = dict(total_profit=0.0, total_commission_paid_usdt=0.0, ...)
    defaults.update(overrides)
    return Bot(**defaults)
```

В тесте тогда видно ровно то, что для него существенно: `make_trade(profit_usdt=0.0)`.

Фабрики намеренно **локальны для файла**, а не вынесены в общий модуль: у разных
тестов разные «разумные дефолты», и общая фабрика быстро обросла бы флагами.

### 3. Fake-объекты вместо моков

В проекте нет `unittest.mock`. Вместо него — маленькие классы с говорящим именем и
docstring, объясняющим, что именно подменяется:

```python
class FakeExchangeRateService:
    """Fake вместо реального ExchangeRateService — не ходит в сеть."""

    def __init__(self, rate: float | None):
        self._rate = rate

    async def get_usdt_rub(self):
        return self._rate
```

Так тест читается как описание поведения, а не как настройка мока, и падает с
понятным `AttributeError`, если продакшн-код начал звать что-то новое.

Отдельный случай — **шпион**: когда важен сам факт вызова, а не результат.
`SpyCommissionService` в `test_polling_worker.py` считает вызовы, но настоящую работу
не подменяет.

### 4. Комментарий объясняет «почему», а не «что»

Это главное отличие тестов в этом проекте. Строка `assert result == -66.67` не говорит
ничего; рядом обязан быть расчёт или причина:

```python
# Assert: max_dd = -100, peak = 150 => -100/150*100 = -66.67%
assert result == -66.67
```

Особенно это касается **неочевидных решений продукта**, которые легко «починить» по
интуиции и сломать:

```python
# сделка с profit_usdt=0.0 в коде считается поражением (profit <= 0),
# поэтому побед 2, а не 3
assert stats.trades_win == 2
```

Тест здесь работает как документация: он фиксирует, что так задумано.

### 5. monkeypatch — по месту использования, а не объявления

```python
monkeypatch.setattr(
    "src.services.commission_service.ExchangeRateService",
    lambda: FakeExchangeRateService(rate=90.0),
)
```

`commission_service` сделал `from ... import ExchangeRateService`, то есть положил имя
к себе в модуль. Подмена в модуле-источнике на уже импортированное имя не подействует.
Правило: патчить там, **куда** импортировали, а не **откуда**.

`monkeypatch` сам всё откатывает после теста — руками возвращать ничего не нужно.

### 6. `# type: ignore` на фейках

Фейки не наследуют настоящие классы, поэтому статический анализатор ругается на
несовпадение типов. Помечайте строку и идите дальше:

```python
service = StatsService(bot_repo=None, trade_repo=FakeTradeRepo(trades))  # type: ignore
```

### 7. Имя теста — это утверждение

Не `test_stats_1`, а `test_zero_profit_trade_counts_as_loss`. По списку упавших тестов
должно быть понятно, что сломалось, без открытия файла. Имена — на английском,
комментарии и docstring — на русском (тот же раскол, что и в остальном проекте:
логи по-английски, тексты пользователю по-русски).

## Что покрыто и почему именно это

Тесты писались не «для процента покрытия», а вокруг мест, где ошибка дорого стоит
и где её не видно глазами.

### `test_comission_service.py` — деньги

Единственное место, где сервис трогает `User.service_balance`. Покрыты все ветки и
границы: прибыль, убыток, **ноль** (комиссия строго с `profit > 0`), `profit_usdt=None`,
недоступный курс (→ `ValueError`) и **повторный вызов на той же сделке**.

Последнее — самое важное. Флаг `trade.commission_paid` это единственный барьер против
двойного списания реальных денег, а `polling_worker` крутится каждые 30 секунд.

Флаг означает «сделка учтена», а не «комиссия списана»: он ставится и на убыточных,
и на нулевых сделках, а ранний `return` по нему прикрывает заодно и `bot.total_profit`.
Тесты держат обе половины этого поведения — и что баланс трогается только при
`profit > 0`, и что повторный вызов не меняет вообще ничего.

Там же зафиксирован **известный изъян кода** (тест его не «одобряет», а не даёт
ему стать сюрпризом): при недоступном курсе `bot.total_profit` уже обновлён до выброса
`ValueError`, то есть объект в памяти остаётся грязным (в проде спасает `db.rollback()`).

### `test_polling_worker.py` — живость ботов и сделки

Правило «бот мёртв после `MAX_PING_MISSES` промахов подряд» руками не проверишь:
надо ронять контейнер и ждать полторы минуты. Здесь оно проверяется за миллисекунды,
потому что счётчик промахов передан в функцию явным аргументом.

Покрыто: порог промахов (и что до порога бот жив), сброс счётчика при ответе,
снятие счётчика после отказа, доставка причины отказа в critical-алерт **и** то, что
сырой текст ошибки не утекает в пользовательский `error_message`, остановка контейнера,
`state: stopped` как отказ и `paused` как норма.

Вторая половина файла — `_async_bot_trades`: создание новой сделки, дедупликация по
`freqtrade_trade_id`, переход открытой сделки в закрытую, направление из `is_short`,
плечо из бота, пропуск синхронизации без владельца, пакет из нескольких сделок и один
коммит на весь пакет.

### `test_stats_service.py` — арифметика

Считать P&L и просадку по 5–10 сделкам на бумажке долго и легко ошибиться. Правильный
ответ посчитан один раз здесь, дальше pytest сверяет с ним код при каждом запуске.

### `test_assistant_suggestions.py` — недоверенный ввод

Модель — источник произвольных данных: может предложить плечо x300, несуществующий
индикатор или строку вместо числа, и всё это уезжает прямо в форму создания бота.
Покрыты диапазоны, шаг ползунка, неизвестные поля, фильтры, дубли, лимит в 8 штук
и оборванный JSON.

Отдельно стоит `test_every_advertised_field_survives_normalization`: он проверяет, что
`SUGGESTABLE_FIELDS` (то, что обещано модели) и ветки `_normalize_value` (то, что
реально принимается) не разъехались. Это самая вероятная ошибка при добавлении поля.

### `test_auth_service.py` + `integration/test_auth.py` — вход в систему

Юниты — на логику (пароль хешируется, неверный пароль отвергается, дубликат email →
`ConflictError`). Интеграционные — на HTTP-контракт (201/409/401/200 и форма ответа).

## Слепые зоны, о которых нужно знать

Честный список. Не «баги», а места, где тест **не поймает** ошибку — учитывайте при
правках.

**1. Фейковые репозитории не выполняют SQL.** `FakeTradeRepo` в `test_stats_service.py`
отдаёт заранее заданный список независимо от запроса. Поэтому сортировка и фильтр по
периоду проверяются косвенно — по тому, что сервис *попросил* у запроса
(`_FakeQuery` записывает вызовы `.where()` / `.order_by()`). Ошибку в самом SQL —
например, неверное условие в `TradeRepository` — так не увидеть.

**2. `flush()` у фейковой сессии ничего не делает.** `default=False` у колонки
применяется настоящим INSERT'ом, поэтому у объекта, созданного в тесте,
`commission_paid` равен `None`, а не `False`. Проверяйте смысл (`assert not
trade.commission_paid`), а не представление.

**3. `lifespan()` не выполняется.** Всё, что происходит при старте приложения —
подготовка папки ботов, Docker-сеть, запуск `polling_worker` — не покрыто.

**4. Поведение самих ботов не тестируется вообще.** Стратегия, шаблон конфига,
`docker_manager`, реальные ответы freqtrade — вне зоны тестов. Проверяется только
в dry-run вручную.

**5. Не покрыты:** `payment_service` (YooKassa, вебхуки, whitelist IP),
`bot_service` (создание/запуск/удаление бота), `exchange_api_key` (шифрование Fernet),
`strategy_presets`, `get_portfolio_stats` и `get_home_stats`.

**6. Миграции не проверяются тестами.** Тесты строят схему напрямую из
`Base.metadata.create_all()` и про alembic ничего не знают. Модель поменялась →
тестовые таблицы создадутся заново, и набор пройдёт, **даже если миграцию забыли
сгенерировать**. Ловит это только `alembic check`, см.
[docs/database/](../database/README.md).
