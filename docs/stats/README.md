# Статистика

Цифры, которые видит пользователь: главная страница и страница `/stats`.

## 1. Что это

Два экрана:

- **`/home`** — сводка: баланс сервиса, прибыль за всё время, сколько ботов запущено,
  прибыль за неделю, сумма в управлении.
- **`/stats`** — страница статистики: сайдбар со списком ботов, переключатель периода
  (1Д / 1Н / 1М), график накопленного P&L, winrate, просадка, таблица последних сделок.
  Режим «Все боты» — агрегат по портфелю, выбор бота — детализация по нему.

`StatsService` **никуда не ходит по сети** — только читает таблицы `trades` и `bots`.
Всё, что попадает в статистику, кладёт туда фоновый воркер.

## 2. Поток данных

```
freqtrade-контейнер каждого бота
   │  GET /api/v1/trades  (каждые 30 c, polling_worker)
   ▼
polling_worker._async_bot_trades
   ├ новой сделки нет в БД      → INSERT в trades
   ├ сделка закрылась           → UPDATE trades
   │                              └ CommissionService.process_commission()
   │                                   ├ Bot.total_profit += profit
   │                                   └ комиссия с прибыльных → User.service_balance
   ▼
таблицы trades / bots  ←── единственный источник статистики
   │
   │ SELECT, без сети
   ▼
StatsService
   ├ get_home_stats()      → GET /stats/home
   ├ get_portfolio_stats() → GET /stats/portfolio?period=…
   └ get_bot_stats()       → GET /stats/bots/{bot_id}?period=…
   ▼
frontend: app/home/page.tsx, app/stats/page.tsx (chart.js)
```

Задержка появления сделки в статистике — до одного цикла воркера (`POLL_INTERVAL = 30 c`).

## 3. Эндпоинты

Все под `get_current_user`, префикс роутера `/stats`.

| Метод | Путь | Параметры | Ответ |
|---|---|---|---|
| GET | `/stats/home` | — | `HomeStats` |
| GET | `/stats/portfolio` | `period` | `PortfolioStats` |
| GET | `/stats/bots/{bot_id}` | `period` | `BotStats` |

`period` — `1D` / `1W` / `1M` / `all`, дефолт `1W`. Маппинг в дни — `PERIOD_MAP`
в `routers/stats.py`. Фронт предлагает только первые три; `all` доступен через API.

Чужой, несуществующий и архивированный бот отдают одинаковый `404 {"detail": "Бот не найден"}` —
по коду ответа нельзя узнать, существует ли бот с таким id.

Схемы ответов — `schemas/stats.py`: `HomeStats`, `PortfolioStats`, `BotStats`,
`BotSummary` (строка сайдбара), `PnlPoint`, `TradeOut`.

## 4. Главный инвариант

**Все числа за период считаются по одному и тому же набору сделок.** Репозиторий
отдаёт одну выборку, из неё считаются `profit`, `winrate`, просадка, график и таблица
сделок. Поэтому последняя точка графика всегда сходится с карточкой «Общий P&L».

Отсюда два следствия, которые легко нарушить по невнимательности:

- **`Bot.total_profit` на странице статистики не используется.** Это инкрементальный
  счётчик за всё время, он ничего не знает о выбранном периоде. Его читает только
  `/stats/home`. В ответах `/stats/portfolio` и `/stats/bots/{id}` поле называется
  `profit` и считается по сделкам.
- **Сортировка — часть контракта репозитория.** `get_closed_trades()` всегда добавляет
  `ORDER BY close_time`, потому что расчёт накопленного P&L и просадки идёт по списку
  подряд. На неотсортированном списке они молча дадут неверный результат.

## 5. Мягкое удаление ботов

`delete_bot` удаляет контейнер и папку бота, но строку в БД только помечает
`is_active = False` (`BotRepository.archive_bot`). Физического `DELETE` нет намеренно:
у `trades.bot_id` стоит `ondelete="CASCADE"`, и удаление бота уносило бы всю его историю —
общий P&L, winrate и график менялись бы задним числом.

Что это значит для статистики:

| | Архивированный бот |
|---|---|
| `GET /bots`, сайдбар `/stats` | не показывается |
| `GET /stats/bots/{id}` | 404 |
| Агрегат портфеля (profit, winrate, график) | **его сделки учитываются** |
| `total_profit` на главной | **учитывается** |
| Счётчики ботов, сумма в управлении | не учитывается |
| Порт из `BOT_API_PORT_RANGE` | освобождается (`get_all_busy_ports` смотрит только активных) |

## 6. Карта файлов

| Файл | Ответственность |
|---|---|
| `backend/src/routers/stats.py` | Три ручки, `PERIOD_MAP`, проверка владельца бота |
| `backend/src/schemas/stats.py` | Схемы ответов |
| `backend/src/services/stats_service.py` | Все расчёты; чистые хелперы + три метода-сборщика |
| `backend/src/repositories/trade_repository.py` | `get_closed_trades()` — единственный источник сделок |
| `backend/src/repositories/bot_repository.py` | `get_user_active_bots()` / `get_user_bots()` / `archive_bot()` |
| `backend/src/models/trade.py`, `models/bot.py` | Таблицы `trades` / `bots` |
| `backend/src/services/polling_worker.py` | Наполняет `trades` (не часть статистики, но её источник) |
| `backend/src/services/commission_service.py` | Обновляет `Bot.total_profit`, списывает комиссию |
| `backend/tests/unit/test_stats_service.py` | Тесты всех метрик на fake-репозиториях |
| `frontend/app/stats/page.tsx` | Страница статистики целиком (графики chart.js) |
| `frontend/app/home/page.tsx` | Карточки главной |

## 7. Эксплуатация

**Нагрузка.** Один запрос портфеля = 2 SELECT (боты + сделки за период), независимо от
количества ботов: сводка для сайдбара считается из той же выборки в памяти.
Ограничения по количеству строк в SQL нет — при `period=all` в память поднимаются все
закрытые сделки пользователя.

**Логи.** `info` на входе и выходе каждого метода (`user_id`/`bot_id`, `period_days`,
итоговые счётчики), `debug` на построении графика и просадки. `logger.critical` не
используется: сервис только читает БД, будить разработчика тут нечем.

**Падать нечему.** Сети нет, деления на ноль защищены, пустые списки возвращают нули
и `None` (см. [metrics.md](metrics.md#крайние-случаи)).

## 8. Известные ограничения

- **`dry_run` и реальные боты не разделены.** У `Trade` нет признака симуляции, поэтому
  сделки бота в режиме `dry_run` попадают в статистику наравне с реальными. По той же
  причине `CommissionService` берёт комиссию и с прибыли симулированных сделок —
  стоит проверить, задумано ли так.
- **`Bot.total_profit` и сумма `Trade.profit_usdt` — два независимых счётчика** и могут
  разъехаться (например, если сделка была учтена до сбоя транзакции). На `/stats` это
  уже не влияет — там всё считается по сделкам, — но на главной цифра берётся из счётчика.
- **Ось X графика категориальная**: точки равноудалены независимо от реального
  интервала между сделками. Для перехода на временную шкалу нужен адаптер дат chart.js.
- **`avg_profit_pct` — простое среднее процентов**, без веса по размеру позиции.
- **Нет пагинации** ни в графике, ни в таблице сделок.
