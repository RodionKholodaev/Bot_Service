# Freqtrade в Bot_Service

Каждый бот в проекте — это отдельный контейнер `freqtradeorg/freqtrade:stable` с
собственным `config.json` и собственным файлом стратегии. Бэкенд сам с биржей не
разговаривает: он генерирует эти два файла, запускает контейнер и потом только
опрашивает его REST API.

Этот документ — про то, **что означает каждая настройка** в обоих файлах и какие
тонкости freqtrade уже успели дорого обойтись в этом проекте.

## Как это собрано

```
пользователь заполняет форму
        ↓
BotCreate (схема)  →  строка в таблице bots
        │              проценты TP/SL → доли маржи (BotService._build_*)
        │              пресет → списки фильтров (resolve_filters)
        ↓
BotFileManager.materialize_bot_files()
        ├── freqtrade_config.generate_config()    → bots_data/<bot_id>/config.json
        └── freqtrade_strategy.generate_strategy_file()
                                                  → bots_data/<bot_id>/user_data/strategies/MultiFilterStrategy.py
        ↓
docker_manager.run_bot_container()   → контейнер freqtrade, порт 8080 → bot.api_port
        ↓
polling_worker каждые 30 с           ← /api/v1/ping, /trades, /show_config
        ├── бот не отвечает 90 с            → status="error" + алерт разработчику
        ├── freqtrade в state "stopped"     → то же
        └── новые/закрытые сделки           → таблица trades + комиссия сервиса
```

Файлы, которые здесь участвуют:

| Файл | Роль |
|---|---|
| [config.template.json](../../backend/src/templates/config.template.json) | Шаблон конфига. Общий для всех ботов |
| [multifilter_strategy.template](../../backend/src/templates/multifilter_strategy.template) | Шаблон стратегии с плейсхолдерами `{{...}}` |
| [freqtrade_config.py](../../backend/src/services/freqtrade_config.py) | Подставляет в шаблон настройки бота |
| [freqtrade_strategy.py](../../backend/src/services/freqtrade_strategy.py) | То же для стратегии, через `repr()` |
| [bot_file_manager.py](../../backend/src/services/bot_file_manager.py) | Создаёт папку бота и пишет оба файла |
| [bot_service.py](../../backend/src/services/bot_service.py) | Проценты → доли маржи, жизненный цикл бота (create/start/stop/delete) |
| [strategy_presets.py](../../backend/src/services/strategy_presets.py) | Пресет → списки фильтров |
| [docker_manager.py](../../backend/src/services/docker_manager.py) | Запуск контейнера, порты, монтирование, права на папку |
| [polling_worker.py](../../backend/src/services/polling_worker.py) | Следит за живостью бота и тянет из него сделки |
| [freqtrade_client.py](../../backend/src/services/freqtrade_client.py) | Синхронный клиент к API бота для обработчиков FastAPI |
| [tradeMath.ts](../../frontend/app/bot-creation/tradeMath.ts) | Показывает пользователю, во что превратятся его проценты |

> **Файлы генерируются один раз — при создании бота.** Правка шаблона или генератора
> не действует на уже созданных ботов, даже после перезапуска контейнера. Чтобы
> починка подействовала, бота надо пересоздать или переписать его `config.json`
> руками (см. [how-to.md](how-to.md)).

## Словарь терминов

**Ставка / маржа (stake)** — сколько своих денег бот кладёт в одну сделку.
В конфиге это `stake_amount`. Не путать с депозитом: депозит — весь капитал бота,
ставка — размер одной сделки.

**Объём позиции (notional)** — сколько денег работает на рынке. `маржа × плечо`.
При марже 20 USDT и плече x10 позиция составляет 200 USDT.

**Плечо (leverage)** — во сколько раз позиция больше маржи. Увеличивает и прибыль,
и убыток, и комиссию — всё в одинаковой пропорции.

**Изолированная маржа (`margin_mode: isolated`)** — под каждую позицию выделяется
своя маржа, и потерять в одной сделке больше неё нельзя. Противоположность —
`cross`, где под угрозой весь счёт. У нас везде `isolated`.

**Ликвидация** — биржа принудительно закрывает позицию, когда убыток съел маржу.
При плече x10 для этого достаточно движения цены на ~10% против позиции.

**Dry run** — режим симуляции. Freqtrade считает сделки по реальным ценам, но
ордера на биржу не отправляет. Кошелёк виртуальный (`dry_run_wallet`).

**Таймфрейм (timeframe)** — размер свечи: `1m`, `5m`, `1h`. Бот принимает решение
один раз на закрытии свечи своего базового таймфрейма.

**Информативный таймфрейм (informative pair)** — дополнительная свечная серия
поверх базовой. Нужен, когда фильтры смотрят сразу на несколько таймфреймов.

**Whitelist** — список пар, которыми боту разрешено торговать. У нас всегда одна пара.

**Формат фьючерсной пары** — `ETH/USDT:USDT`. До двоеточия — торгуемая пара, после —
валюта расчёта (settlement). Для спота двоеточия не было бы.

**Taker / maker** — тейкер забирает заявку из стакана (ордер исполняется сразу,
комиссия выше), мейкер ставит свою заявку и ждёт (комиссия ниже).

**ROI (`minimal_roi`)** — правило «закрыть сделку, когда прибыль достигла X».
Это и есть take profit в терминах freqtrade. X задаётся **в долях маржи**.

**Trailing stop** — стоп, который подтягивается за ценой, когда сделка в плюсе.
У нас выключен, см. [Ловушки](#трейлинг-с-дефолтными-константами-убыточен).

**Круг (round trip)** — вход плюс выход. Комиссия почти всегда считается за круг:
одна цифра вместо двух.

**`state` бота** — состояние торгового цикла freqtrade, отдельное от статуса
контейнера и от нашего `bots.status`: `running` — торгует, `paused` — пауза (штатно),
`stopped` — цикл встал. Видно в `GET /api/v1/show_config`.

## Главное: пользователь задаёт движение цены, freqtrade считает от маржи

Самая дорогая тонкость проекта. Freqtrade меряет `minimal_roi`, `stoploss` и трейлинг
**в долях маржи** — то есть уже с учётом плеча. Проценты, которые пользователь вводит
в форме, — наоборот, **движение цены**: «take profit 1.5%» значит «цена прошла полтора
процента», при любом плече.

Перевод одного в другое живёт ровно в двух функциях
[bot_service.py](../../backend/src/services/bot_service.py) и больше нигде:

```python
BotService._build_take_profit(1.5, leverage=10)     # -> {"0": 0.15}
BotService._build_stoploss(True, 1.0, leverage=10)  # -> -0.10
```

```
доля маржи = процент пользователя × плечо / 100
```

| Ввёл пользователь | Плечо | Уедет в freqtrade | Что это значит в деньгах |
|---|---|---|---|
| TP 1.5% | x10 | `minimal_roi = {"0": 0.15}` | цена прошла 1.5% → +15% маржи |
| TP 1.5% | x3 | `minimal_roi = {"0": 0.045}` | цена прошла 1.5% → +4.5% маржи |
| SL 1% | x10 | `stoploss = -0.10` | цена прошла 1% → −10% маржи |
| SL выключен | любое | `stoploss = -0.99` | держим почти до ликвидации |

**Плечо здесь — множитель результата, а не цели.** Оно не меняет ни точку выхода по
цене, ни соотношение выигрыша к проигрышу; оно умножает и прибыль, и убыток, и
комиссию в одинаковой пропорции. Это и есть смысл того, что проценты заданы в
движении цены.

⚠️ **Так стало с коммита `5e1efd8` (26 августа 2026).** До него умножения не было:
процент уезжал во freqtrade как есть, и «TP 1.5%» при x10 означало 0.15% движения
цены — в десять раз ближе ожидаемого и внутри спреда. Отсюда два следствия, о которых
надо помнить, читая старые данные и старые файлы:

- **Файлы бота генерируются один раз при создании.** Боты, созданные до этого
  коммита, продолжают торговать по старым числам: у них в `MultiFilterStrategy.py`
  лежит `minimal_roi = {"0": 0.015}` вместо `{"0": 0.15}`. Пересоздание — единственный
  способ перевести их на новую трактовку, см. [how-to.md](how-to.md#применить-починку-к-уже-работающему-боту).
- **Вся статистика на 1722 боевых сделках ниже снята со старой трактовки.** Как
  измерение комиссии она остаётся верной (комиссия от трактовки не зависит), как
  пример настроек — уже нет.

### Границы, которые проверяет `BotCreate`

Стоп задан движением цены, а сработать он должен раньше ликвидации. Отсюда проверка в
[schemas/bot.py](../../backend/src/schemas/bot.py):

```
stop_loss_percent × leverage < 100
```

Иначе `stoploss <= -1`, а такого freqtrade не принимает: контейнер падал при старте, и
бот создавался «успешно», но сразу уходил в `error`. Сообщение пользователю называет
максимум для его плеча (`100 / leverage` процентов движения цены).

Расстояние до ликвидации оценивается тем же числом: **≈ `100 / плечо` процентов
движения цены**. При x10 это 10%, при x25 — 4%.

### Комиссия

Комиссия берётся с **объёма позиции**, а маржа в `плечо` раз меньше. Значит в
процентах от маржи она во столько же раз больше:

```
комиссия от маржи ≈ 0.06% × плечо        (0.06% — круг: вход + выход, от цены)
```

При x10 круг стоит ~0.6% маржи. ✅ Величина 0.06% выведена из фактических сделок
(разница между заданным стопом и реальным убытком, делённая на плечо) и сходится с
тарифами Bybit на перпетуалах (taker 0.055%, maker 0.02%): вход у нас `market`,
выход `limit`, круг ложится между 0.04% и 0.11%.

Важно: **комиссия нигде в конфиге бота не задаётся**. Freqtrade берёт ставку через ccxt
у самой биржи — в live из фактически исполненного ордера, в dry-run из market data.
Константа `ROUND_TRIP_FEE_PERCENT = 0.06` в
[tradeMath.ts](../../frontend/app/bot-creation/tradeMath.ts) нужна только чтобы
показать пользователю порядок величины на шаге 4 формы; на торговлю она не влияет.

### Отсюда — асимметрия TP и SL

- **ROI считается после комиссии.** Freqtrade сравнивает `minimal_roi` с чистой
  прибылью, поэтому выигрыш в деньгах равен ровно заданному TP — но **цене** надо
  пройти на комиссию больше: `TP + 0.06%`.
- **Stoploss считается по цене, без комиссии.** Стоп ставится в правильную цену, а
  реальный убыток выходит больше на всю комиссию: `SL + 0.06%` движения цены.

Как это выглядело на боевых данных (⚠️ боты старой трактовки — колонка «задан SL»
там означала долю маржи, а не движение цены):

| Бот | Плечо | Задан SL | Реальный убыток | Разница |
|---|---|---|---|---|
| AVAX | x10 | −1.0% | **−1.63%** | комиссия 0.63% ≈ 0.06 × 10 |
| ADA | x3 | −1.5% | **−1.65%** | 0.15% ≈ 0.06 × 3 |
| SOL | x10 | −2.0% | **−2.67%** | 0.67% |
| ETH | x5 | −1.0% | **−1.35%** | 0.35% |

### Отсюда — нужный винрейт

```
нужный винрейт = (SL + комиссия) / (TP + SL + комиссия)
```

Плечо в этой формуле сокращается — оно множит и числитель, и знаменатель. При
«TP 1.5% / SL 1%» и комиссии 0.06%: `1.06 / 2.56` = **41 сделка из 100**, и это число
одинаково для x1 и для x25.

Это оценка **до начала торговли**, из заданных настроек — ровно её считает
`computeTradeMath()` и показывает на шаге 4 формы создания бота. Постфактум винрейт
считают по фактическим средним: у AVAX-бота средний плюс вышел 2.13% маржи, средний
минус 1.85%, то есть безубыточность требовала 46 сделок из 100. Фактически он выиграл
**22.7%** — отсюда убыток в 373 USDT.

**Связка «маленький TP + большая комиссия» убыточна арифметически, до всякой
стратегии.** Форма предупреждает об этом, когда `TP < 5 × комиссии` — см.
`collectTradeWarnings()` там же.

## Из чего складывается настройка бота

Соответствие между интерфейсом, базой и freqtrade. Колонки в БД названы неудачно —
это исторический след, помнить обязательно:

| Поле формы | Колонка в `bots` | Ключ freqtrade | Смысл |
|---|---|---|---|
| Депозит бота | `stake_amount` ⚠️ | `dry_run_wallet` + `available_capital` | Весь капитал бота |
| Размер сделки, % | `tradable_balance_ratio` ⚠️ | — (множитель) | Доля депозита на сделку |
| — | — | `stake_amount` | `депозит × доля` |
| Пара | `pair` | `exchange.pair_whitelist` | Одна пара на бота |
| Плечо | `leverage` | `LEVERAGE` в стратегии | |
| Направление | `direction` | `CAN_SHORT` + какие фильтры заполнены | long / short / both |
| Take profit, % цены | `take_profit` | `minimal_roi` | `1.5` при x10 → `{"0": 0.15}` |
| Stop loss, % цены | `stop_loss` | `stoploss` | `1` при x10 → `-0.10`; выключен → `-0.99` |
| — | `trailing_stop` | `trailing_stop` | ⚠️ всегда `False`, поля в форме нет |
| Режим | `dry_run` | `dry_run` | |
| Индикаторы | `entry_filters_long` / `_short` | `ENTRY_FILTERS_*` | JSON-список правил |
| Пресет | `strategy_preset` | — | Раскрывается в фильтры при создании |
| Ключ биржи | `api_key_id` | `exchange.key` / `secret` | Только свой ключ, проверка в `create_bot` |

Обратите внимание: в колонках `take_profit` / `stop_loss` лежит уже **доля маржи**, а
не то, что вводил пользователь. Обратно процент движения цены восстанавливается
делением на `leverage`. Отдельно исходный ввод нигде не хранится.

### Что валидируется на входе

[`BotCreate`](../../backend/src/schemas/bot.py) — единственная защита: дальше значения
попадают в JSON конфига и в исполняемый Python стратегии.

| Поле | Ограничение | Почему |
|---|---|---|
| `leverage` | `1 … 125` | Верх — предел биржи, ниже единицы плеча не бывает |
| `take_profit_percent` | `> 0`, `≤ 100` | Движение цены |
| `stop_loss_percent` | `> 0`, `≤ 100`, и `× leverage < 100` | Стоп в целую маржу — это `stoploss <= -1`, freqtrade такого не берёт |
| `stake_amount` (депозит) | `> 0` | Без границы 0 или минус доезжал до конфига, и бот молча не торговал |
| `tradable_balance_ratio` (доля) | `> 0`, `≤ 1` | Сделка не может быть больше депозита |
| `entry_filters_*` | Обязательны по направлению | `long`/`both` → нужны длинные, `short`/`both` → короткие |
| `FilterRule` | `Literal[...]` на индикатор, таймфрейм, условие | Эти строки уезжают в шаблон стратегии как код |

⚠️ **`Bot.stake_amount` хранит депозит, а не размер сделки**, а
`Bot.tradable_balance_ratio` — долю депозита на сделку, а не одноимённый ключ
freqtrade. Имена остались от первой, неверной трактовки. Переименование потребует
миграции и правок в `stats_service`, поэтому пока живём с комментарием в модели.

## config.json — поле за полем

Значения в шаблоне, которые генератор перезаписывает, помечены **(генерируется)**.

### Капитал и размер сделки

| Ключ | Значение | Что делает |
|---|---|---|
| `stake_amount` | **(генерируется)** `депозит × доля` | Сколько своих денег в одной сделке. Может быть числом или `"unlimited"` |
| `dry_run_wallet` | **(генерируется)** депозит | Стартовый баланс виртуального кошелька. Работает только в dry run |
| `available_capital` | **(генерируется)** депозит | Сколько боту разрешено взять с реального счёта биржи. Нужен, чтобы бот не считал своим весь баланс |
| `max_open_trades` | `1` | Сколько сделок одновременно. У нас всегда одна |
| `stake_currency` | `USDT` | Валюта расчёта |
| `tradable_balance_ratio` | **удалён из шаблона** | Доля всего счёта под торговлю. `available_capital` его перекрывает — держать оба значит гадать, какое сработало |

> `available_capital` не конфликтует с `tradable_balance_ratio` с ошибкой, он его
> **молча заменяет**. Именно поэтому второй убран из шаблона совсем.

### Режим торговли

| Ключ | Значение | Что делает |
|---|---|---|
| `dry_run` | **(генерируется)** | `true` — симуляция без ордеров на бирже |
| `trading_mode` | `futures` | Фьючерсы, а не спот. Без этого не работает плечо и шорт |
| `margin_mode` | `isolated` | Изолированная маржа: убыток ограничен маржой позиции |
| `liquidation_buffer` | `0.05` | Отступ 5% от цены ликвидации — freqtrade закроет позицию раньше биржи |
| `initial_state` | `running` | Бот начинает торговать сразу после старта контейнера |
| `cancel_open_orders_on_exit` | `false` | При остановке бота висящие ордера не отменяются |
| `force_entry_enable` | `false` | Запрещает принудительный вход через API |

### Цены и ордера

| Ключ | Значение | Что делает |
|---|---|---|
| `entry_pricing.price_side` | `other` | Вход по «противоположной» стороне стакана — для лонга это ask, то есть исполнение сразу |
| `entry_pricing.use_order_book` + `order_book_top: 1` | `true`, `1` | Цена берётся из стакана, первый уровень |
| `exit_pricing.price_side` | `same` | Выход по «своей» стороне — заявка ждёт, пока цена дойдёт. Дешевле по комиссии, но исполняется не всегда |
| `entry_pricing.price_last_balance` | `0.0` | Смешивание цены стакана с last price: 0 — берём только стакан |
| `entry_pricing.check_depth_of_market` | `enabled: false` | Проверка перекоса стакана перед входом. Выключена |
| `exit_pricing.use_order_book` + `order_book_top: 1` | `true`, `1` | Цена выхода тоже из первого уровня стакана |
| `unfilledtimeout.entry/exit` | `10` минут | Неисполненный ордер отменяется |
| `unfilledtimeout.exit_timeout_count` | `0` | Сколько раз подряд можно не исполнить выход, прежде чем закрыть рынком. 0 — без ограничения |

### Биржа и пары

| Ключ | Значение | Что делает |
|---|---|---|
| `exchange.name` | `bybit` | Единственная поддерживаемая биржа |
| `exchange.key` / `secret` | **(генерируется)** | Расшифрованный ключ из `exchange_api_keys`. В dry run пустые строки |
| `exchange.pair_whitelist` | **(генерируется)** | Ровно одна пара — та, что выбрал пользователь |

падение контейнера на старте, которое воркер увидит через 90 секунд и переведёт бота

### Что задаёт не конфиг, а докер

Смотреть в [docker_manager.run_bot_container()](../../backend/src/services/docker_manager.py):

- папка бота монтируется в `/freqtrade/user_data_mount`;
- база сделок самого freqtrade — `sqlite:////freqtrade/user_data_mount/user_data/tradesv3.sqlite`
  (отдельная от нашей `cryptobot.db`);
- `restart_policy: on-failure`, максимум 5 попыток;
- `mem_limit: 512m` на контейнер;
- стратегия ищется по имени класса `MultiFilterStrategy`, путь к ней задаётся
  `--strategy-path`, данные свечей — `--datadir`;
- все боты сидят в одной сети `cryptobot-network` (`DOCKER_NETWORK_NAME`), она
  создаётся при старте бэкенда в `lifespan()`;
- образ (`FREQTRADE_IMAGE`, по умолчанию `freqtradeorg/freqtrade:stable`) при первом
  запуске бота подтягивается `ensure_image()` — первый старт на чистом сервере
  занимает минуты, а не секунды;
- имя контейнера — `bot_<первые 24 символа uuid без дефисов>`. Если контейнер с таким
  именем уже есть, `run_bot_container()` **останавливает и удаляет старый** и поднимает
  новый; открытые сделки при этом переживают пересоздание — они в примонтированной
  `tradesv3.sqlite`.

**`set_bot_permissions()` — про права на папку бота.** Внутри контейнера freqtrade
работает от `ftuser` (UID 1000), а папку создаёт бэкенд от своего пользователя.
Перед запуском делается `chown -R 1000:1000`. На Windows шаг пропускается (там прав
Unix нет и Docker Desktop сам разбирается), на Linux без него freqtrade не сможет
писать в `tradesv3.sqlite` и упадёт на старте. Если бэкенд запущен не от root и не от
владельца — `chown` бросит `PermissionError`, и бот уйдёт в `error` уже на старте.

## Файл стратегии — поле за полем

Генерируется из [multifilter_strategy.template](../../backend/src/templates/multifilter_strategy.template)
простым `.replace()` плейсхолдеров на `repr()` значений. Никакой песочницы нет —
всё, что попадает в шаблон, становится исполняемым Python внутри контейнера.

### Блок StrategyConfig — то, что подставляет бэкенд

| Плейсхолдер | Откуда | Что означает |
|---|---|---|
| `{{BASE_TIMEFRAME}}` | вычисляется | Минимальный таймфрейм среди всех фильтров |
| `{{LEVERAGE}}` | `bot.leverage` | Плечо |
| `{{CAN_SHORT}}` | `direction in ("short","both")` | Разрешён ли шорт |
| `{{ENTRY_FILTERS_LONG}}` / `{{..._SHORT}}` | колонки `entry_filters_*` | Списки правил входа |
| `{{TAKE_PROFIT}}` | `bot.take_profit` | Уходит в `minimal_roi`. Уже доля маржи |
| `{{STOPLOSS}}` | `bot.stop_loss` | Отрицательная доля маржи |
| `{{TRAILING_STOP}}` | `bot.trailing_stop` | ⚠️ всегда `False` |

Всё остальное в шаблоне — константы, одинаковые у всех ботов. Если фильтров нет
совсем, `_get_base_timeframe()` пишет `warning` и возвращает `5m`; на практике это
недостижимо — `BotCreate` требует фильтры по направлению.

**Базовый таймфрейм выбирается как минимальный из фильтров** — это не мелочь.
Он задаёт, как часто бот вообще думает: добавление одного фильтра на `1m` к
стратегии из `5m`-фильтров превращает бота из «12 решений в час» в «60 решений в
час». Порядок задан в `TF_ORDER` в [freqtrade_strategy.py](../../backend/src/services/freqtrade_strategy.py).

Правило не случайное: информативный таймфрейм в freqtrade обязан быть **не меньше**
базового. Взяв минимум, мы гарантируем, что все остальные подмешаются корректно.

### Атрибуты стратегии

| Атрибут | Значение | Что делает |
|---|---|---|
| `minimal_roi` | `{"0": 0.15}` | Ключ — **минут с момента входа**, значение — требуемая прибыль в долях маржи. `{"0": 0.15}` = «закрыть при +15% маржи в любой момент» (это TP 1.5% цены при x10). Можно ступеньками: `{"0": 0.05, "30": 0.02}`, мы генерируем всегда одну ступень |
| `stoploss` | `-0.10` | Доля от маржи. Выключенный SL кодируется как `-0.99` |
| `trailing_stop` | `False` | Включён ли трейлинг |
| `trailing_stop_positive` | `0.001` | ⚠️ На сколько отпускать цену от максимума. Доля маржи, и **на плечо не умножается** — в отличие от TP/SL это захардкоженная константа шаблона, а не пользовательский процент. При x10 это 0.01% движения цены |
| `trailing_stop_positive_offset` | `0.002` | С какой прибыли трейлинг включается |
| `trailing_only_offset_is_reached` | `True` | Не трогать позицию, пока offset не достигнут |
| `timeframe` | базовый | Свеча, на которой принимаются решения |
| `startup_candle_count` | `200` | Сколько свечей догрузить перед стартом, чтобы индикаторы посчитались. RSI(14) и CCI(20) требуют заметно меньше — запас |
| `process_only_new_candles` | `True` | Думать один раз на закрытии свечи, а не каждые 5 секунд |
| `use_exit_signal` | `True` | Слушать сигналы выхода... |
| — | | ...но `populate_exit_trend` возвращает нули, то есть **сигналов выхода нет вообще**. Выход только по ROI, стопу или аварийно |
| `exit_profit_only` | `False` | Не ждать плюса перед выходом |
| `ignore_roi_if_entry_signal` | `False` | ROI срабатывает, даже если сигнал на вход ещё активен |
| `can_short` | из `direction` | Без него шорт не откроется, даже если короткие фильтры заданы |
| `INTERFACE_VERSION` | `3` | Версия API стратегий freqtrade |

### Типы ордеров

```python
order_types = {
    "entry": "market",              # вход рынком — исполняется сразу, комиссия тейкера
    "exit": "limit",                # выход лимиткой — дешевле, но может не исполниться
    "stoploss": "market",
    "stoploss_on_exchange": True,   # стоп-ордер живёт на бирже
}
```

```python
order_time_in_force = {"entry": "GTC", "exit": "GTC"}   # good till cancelled
```

`stoploss_on_exchange: True` означает, что стоп поставлен на бирже и сработает, даже
если контейнер бота умер. Обратная сторона — если биржа ордер не приняла, freqtrade
аварийно закрывает позицию (см. [Ловушки](#ловушки)).

`GTC` — заявка висит, пока не исполнится или её не снимут; снимает её у нас
`unfilledtimeout` через 10 минут.

### Метод `leverage()`

```python
return min(StrategyConfig.LEVERAGE, max_leverage)
```

Плечо пользователя ограничивается максимумом биржи для этой пары. То есть заданные
x50 на паре с лимитом x25 молча превратятся в x25.

### `populate_indicators()`

Считает по базовому таймфрейму `RSI(14)` и `CCI(20)`, затем для каждого
дополнительного таймфрейма подмешивает такие же колонки через `merge_informative_pair`
с `ffill=True` (значение старшей свечи «протягивается» на все младшие).

Колонки называются `rsi` / `cci` для базового таймфрейма и `rsi_1h` / `cci_30m` — для
остальных. Внутри `merge_informative_pair` временно даёт имена вида `rsi_1h_1h`, и
шаблон их переименовывает — если менять эту часть, переименование трогать осторожно.

Индикаторы считаются на **всех** дополнительных таймфреймах сразу оба (`rsi` и `cci`),
даже если фильтр смотрит только на один из них — лишняя пара колонок дешевле, чем
разбор того, какие именно нужны.

⚠️ Если `get_pair_dataframe()` вернул пустой датафрейм (данных по этому таймфрейму ещё
нет), таймфрейм **молча пропускается** — колонок `rsi_1h`/`cci_1h` в датафрейме не
появится. Что из этого следует — в [Ловушках](#когда-фильтр-исчезает-бот-входит-на-каждой-свече).

### `populate_entry_trend()` и `populate_exit_trend()`

Вход: `enter_long = 1` там, где сработали все длинные фильтры; `enter_short` — то же,
но только если `CAN_SHORT` **и** короткие фильтры непустые. Пустой список фильтров
означает «этим направлением не торгуем» — условие не строится вообще.

Выход: `populate_exit_trend()` всегда возвращает нули. Сигналов выхода нет, и
единственные способы закрыть сделку — `minimal_roi`, стоп, аварийный выход freqtrade
или ручной `force_exit` через REST API.

## Фильтры входа

Одно правило — словарь из четырёх ключей:

```json
{"indicator": "rsi", "timeframe": "5m", "condition": "less", "value": 50}
```

| Ключ | Допустимые значения |
|---|---|
| `indicator` | `rsi`, `cci` |
| `timeframe` | `1m`, `5m`, `15m`, `30m`, `1h`, `4h` |
| `condition` | `less`, `greater`, `less_equal`, `greater_equal` |
| `value` | число |

Что важно понимать про их применение (`_apply_filters` в шаблоне):

- **Все правила объединяются через И.** Чем больше фильтров, тем реже вход.
- **Автоматически добавляется `volume > 0`** — защита от пустых свечей.
- **Смотрится только текущее значение**, никаких пересечений и сравнений с прошлой
  свечой. Условие «RSI < 50» истинно всё время, пока RSI ниже 50, поэтому бот будет
  входить снова и снова на каждой новой свече.
- **Отсутствующая колонка молча пропускается** — только `logger.warning` внутрь
  контейнера. Опечатка в имени индикатора не сломает бота, она просто снимет фильтр.

Пресеты (`conservative` / `moderate` / `aggressive`) лежат в
[strategy_presets.py](../../backend/src/services/strategy_presets.py). ⚠️ Фронтенд
сейчас всегда отправляет `strategy_preset: "custom"` и передаёт фильтры явно, так
что содержимое `PRESETS` на боевых ботов не влияет.

## Пресеты стратегий

`resolve_filters(preset, direction, custom_long, custom_short)` вызывается один раз при
создании бота и возвращает пару списков. Дальше живут только они: `strategy_preset`
остаётся в БД как пометка, но при генерации стратегии не используется.

| Пресет | Long | Short | Базовый TF |
|---|---|---|---|
| `conservative` | RSI 5m < 30, RSI 15m < 35, CCI 1h < −100 | RSI 5m > 70, RSI 15m > 65, CCI 1h > 100 | `5m` |
| `moderate` | RSI 1m < 40, RSI 5m < 45, CCI 30m < −50 | RSI 1m > 60, RSI 5m > 55, CCI 30m > 50 | `1m` |
| `aggressive` | RSI 1m < 55, CCI 5m < 0 | RSI 1m > 55, CCI 5m > 0 | `1m` |
| `custom` | что прислал фронт | что прислал фронт | минимальный из фильтров |

Две вещи, которые легко упустить:

- **`direction` обрезает лишнюю сторону.** При `long` короткие фильтры очищаются, при
  `short` — длинные, даже если пресет или запрос их содержали.
- **Неизвестный пресет — это `ValueError`** из `resolve_filters`, то есть 500-я ошибка,
  а не 400-я. До сих пор не всплывало, потому что `BotCreate` ограничивает поле
  `Literal[...]` — но эта валидация тут единственная защита.

## REST API бота: что мы у него спрашиваем

У каждого контейнера свой REST API freqtrade: внутри всегда `8080`
(`docker_manager.INTERNAL_API_PORT`), наружу проброшен на `bot.api_port` из диапазона
`BOT_API_PORT_RANGE_START…END` (9000–9999). Порт выдаётся при создании бота
`BotRepository.allocate_port()` — первый свободный среди **активных** ботов; у
архивированных контейнера уже нет, и держать их порты занятыми значило бы рано или
поздно исчерпать диапазон.

### Ручки, которые реально используются

| Ручка | Кто зовёт | Зачем |
|---|---|---|
| `GET /api/v1/ping` | `polling_worker._ping_bot` | Жив ли процесс freqtrade. **Без авторизации** — так неверный пароль не выглядит как смерть бота |
| `GET /api/v1/show_config` | `polling_worker._fetch_bot_state` | Поле `state`: `running` / `paused` / `stopped`. Заодно самый честный способ увидеть, что бот применил |
| `GET /api/v1/trades?limit=500` | `polling_worker._fetch_trades` | Сделки для синхронизации |
| `GET /api/v1/status` | `freqtrade_client.get_status` | Открытые сделки, проксируется на `GET /bots/{id}/freqtrade/status` |
| `GET /api/v1/profit` | `freqtrade_client.get_profit` | Сводка. Функция есть, вызовов нет |

Клиентов два, и это не дублирование по недосмотру:
[freqtrade_client.py](../../backend/src/services/freqtrade_client.py) — синхронный
`httpx.Client` для запросов из обработчиков FastAPI,
[polling_worker.py](../../backend/src/services/polling_worker.py) — свой асинхронный
`httpx.AsyncClient`, живущий всё время работы воркера. Общее у них — адрес
`http://{BOT_API_HOST}:{bot.api_port}` и basic-auth `bot.api_username` /
`bot.api_password` (пароль случайный на каждого бота, `secrets.token_urlsafe(16)`).

### Почему порт биндится в loopback

`BOT_API_BIND_HOST = 127.0.0.1` — не косметика. REST API freqtrade умеет остановить
торговлю и закрыть позиции, а `/ping` там и вовсе без авторизации; на `0.0.0.0` весь
диапазон 9000–9999 торчал бы в интернет за одним basic-auth. Менять только если бэкенд
ходит в ботов не с того же хоста.

⚠️ **Логи бота бэкенд читает не через API freqtrade, а через docker** — `docker logs`
в `docker_manager.get_container_logs()`. Так видно и то, что случилось до подъёма REST
API: при битом конфиге или несуществующей паре freqtrade падает раньше, чем начинает
отвечать.

## Как бэкенд следит за ботом

Статусы в `bots.status` и кто их ставит:

| Статус | Ставит | Когда |
|---|---|---|
| `created` | `create_bot` | Строка и файлы есть, контейнера ещё нет |
| `starting` | `start_bot` | Перед запуском контейнера |
| `running` | `start_bot` | Контейнер поднялся. **Не значит, что freqtrade уже торгует** — он ещё десятки секунд грузит рынки |
| `stopped` | `stop_bot` | Пользователь остановил |
| `error` | `start_bot` / `polling_worker` | Не удалось запустить, либо воркер признал бота мёртвым |

`POST /bots` создаёт бота и **сразу его запускает** — отдельного шага «запустить» в
интерфейсе нет, `POST /bots/{id}/start` нужен только для повторного запуска.

### Проверка живости в `polling_worker`

Каждые `POLL_INTERVAL = 30` секунд по всем ботам со `status = "running"` и
`is_active = True`:

```
/api/v1/ping ── не ответил ──> счётчик промахов +1 ──> 3 промаха подряд (90 с) ──> отказ
      │
      ответил
      ↓
/api/v1/trades ──> синхронизация сделок в нашу таблицу
      ↓
/api/v1/show_config ── state == "stopped" ──> отказ
```

Три решения здесь неочевидны и стоили отладки:

- **Живость меряется по REST API, а не по статусу контейнера.** При отказе на старте
  процесс freqtrade зависает в shutdown (незакрытый non-daemon поток websocket-ов
  ccxt), и docker до бесконечности показывает `running` у мёртвого бота.
- **Одного промаха мало — нужно `MAX_PING_MISSES = 3`.** Столько же длится окно
  перезапуска контейнера по `restart_policy`, а после старта freqtrade ещё грузит
  рынки и пейрлист, уже будучи в статусе `running`.
- **Живой процесс ещё не значит, что бот торгует.** Поймав `OperationalException`,
  freqtrade переводит себя в `state: stopped` и продолжает крутиться пустым циклом —
  контейнер, порт и `ping` при этом полностью здоровы. `paused` — штатное состояние,
  отказом не считается.

Сделки синхронизируются **до** проверки состояния: если ниже окажется, что бот встал,
контейнер будет остановлен и добрать сделки станет неоткуда.

### Что происходит при отказе (`_mark_bot_failed`)

1. Из docker забираются последние 50 строк логов контейнера;
2. `logger.critical` — то есть алерт разработчику в Telegram и событие в Glitchtip
   (в `extra` уезжает только хвост в 1000 символов, полный — в контекст Glitchtip);
3. `status = "error"`, короткая причина в `error_message` — её видит пользователь;
4. **коммит в БД до остановки контейнера** — иначе упавшая остановка оставила бы бота
   `running`, и алерт летел бы каждые 30 секунд;
5. контейнер останавливается: он держит проброшенный порт и до 512 МБ памяти.

Формулировки, которые доезжают до пользователя в `error_message`:

| Текст | Что случилось |
|---|---|
| `Bot API is not responding for 90 seconds` | Три промаха ping подряд |
| `Freqtrade stopped trading (state: stopped)` | Процесс жив, торговый цикл встал |
| Текст исключения docker (обрезан до 500) | Контейнер не удалось запустить вообще |

Счётчик промахов живёт **в памяти процесса** (`ping_misses`), не в БД: цена его потери
при рестарте бэкенда — повторное обнаружение отказа через полторы минуты.

## Как сделки попадают в нашу БД

`_async_bot_trades()` разбирает ответ `/api/v1/trades` (последние 500) и раскладывает
его в таблицу `trades`. Ключ дедупликации — `freqtrade_trade_id` в паре с `bot_id`.

| Поле freqtrade | Колонка `trades` | Примечание |
|---|---|---|
| `trade_id` | `freqtrade_trade_id` | Уникален внутри бота, не глобально |
| `pair` | `pair` | |
| `is_short` | `direction` | `True` → `short` |
| `open_rate` / `close_rate` | те же | `close_rate` заполняется только у закрытых |
| `amount` | `amount` | Размер позиции в базовой валюте |
| `profit_abs` | `profit_usdt` | |
| `profit_ratio` | `profit_pct` | Умножается на 100 |
| `exit_reason` | `exit_reason` | |
| `open_date` / `close_date` | `open_time` / `close_time` | Парсятся `_parse_dt`, при провале — текущее время |
| — | `leverage` | Берётся из `bot.leverage`, а не из ответа freqtrade |

Три правила, каждое из которых написано по следам боевой ошибки:

- **Признак «сделка дозаписана» — это `close_rate`, а не `close_time`.** `close_time`
  проставляется всегда (при отсутствии даты подставляется текущее время), так что по
  нему сделка выглядела бы готовой уже после первого прохода. Так в боевой БД осели
  7 сделок из 1722 с `NULL` в `close_rate`.
- **Учёт закрытой сделки происходит только при `profit_usdt is not None`.** По
  недосчитанному результату `process_commission` взял бы `profit = 0`, поставил
  `commission_paid` и закрыл сделку для учёта навсегда.
- **`not trade.commission_paid` проверяется и здесь, и внутри сервиса.** Freqtrade
  отдаёт последние 500 сделок на каждый опрос — без этой проверки сервис звался бы на
  каждую из них каждые 30 секунд.

Что происходит дальше с прибылью и комиссией — в [docs/stats/](../stats/README.md).

`exit_reason` приходит от freqtrade и хранится в `trades.exit_reason`. Что означает
каждое значение и сколько их встретилось на 1722 боевых сделках:

| Значение | Встретилось | Что произошло |
|---|---|---|
| `roi` | 445 | Достигнут `minimal_roi` — целевая прибыль. **Единственный плановый плюс** |

## Ловушки

Каждая из них уже сработала на боевых данных.

### Ставка больше доступного капитала — бот молча не торгует

Если `stake_amount > available_capital`, freqtrade на каждом цикле бросает
`DependencyException` и не открывает позицию. Не уменьшает ставку, не пишет ошибку в
наш бэкенд — просто ничего не делает. Бот при этом `running` и выглядит здоровым.

✅ Наблюдалось: бот с депозитом 1000 и долей 50% (ставка 1000 при доступных 500)
простоял четверо суток с нулём сделок. ⚠️ Точная причина по логам контейнера не
подтверждалась — вывод сделан по поведению и по коду freqtrade.

Сейчас от этого защищает арифметика генератора (`ставка = депозит × доля`, доля ≤ 1)
и валидация в `BotCreate`.

### Трейлинг с дефолтными константами убыточен

`trailing_stop_positive = 0.001` — это 0.1% **от маржи**, то есть при x10 движение
цены на 0.01%, внутри спреда. Комиссия за круг при этом ~0.6% маржи. Включённый
трейлинг с такими числами фиксировал бы +0.1% против −0.6% расходов на каждой сделке.

В отличие от TP и SL эти константы **не пересчитываются из движения цены** — они
захардкожены в шаблоне как доли маржи, поэтому плечо давит их напрямую.

Переключатель из формы убран (`a27beab`), поля в `BotCreate` нет, `BotService` пишет
`trailing_stop=False` всегда — и это закреплено тестами
`tests/unit/test_bot_trailing_stop.py`. Включение обратно должно красить эти тесты и
требует трёх вещей сразу: осмысленных констант (с пересчётом на плечо, как у TP/SL),
поля через все 10 шагов из [how-to.md](how-to.md#добавить-новое-поле-настройки) и
разбора аварийных выходов — при `stoploss_on_exchange` трейлинг заставляет
перевыставлять стоп-ордер на бирже на каждом новом пике.

### `stoploss_on_exchange` и аварийные выходы

131 сделка закрылась через 5–6 секунд после открытия с убытком ~2% маржи, суммарно
−330.13 USDT (средняя длительность такой сделки — 6 секунд). Похоже на отказ биржи принять стоп-ордер: freqtrade в этом случае
выходит рынком. Пик пришёлся на два дня, потом почти прекратилось.

⚠️ Гипотеза. Подтверждается только логами контейнера, их ещё не смотрели.

### Комиссия ROI и стопа считается по-разному

Описано выше в [арифметике](#отсюда--асимметрия-tp-и-sl). Практический вывод: **не
показывайте пользователю заданный SL как реальный риск** — реальный больше на
`0.06% × плечо`.

### Когда фильтр исчезает, бот входит на каждой свече

`_apply_filters()` пропускает правило, если нужной колонки нет в датафрейме — только
`logger.warning` внутрь контейнера. Но к списку условий **всегда** добавляется
`volume > 0`, а он истинен почти на всех свечах. Значит если отвалятся *все* правила
направления, условие входа выродится в «объём не нулевой», и бот будет открывать
позицию на каждой новой свече базового таймфрейма.

Отвалиться они могут двумя путями, и ни один не является опечаткой разработчика:

- `get_pair_dataframe()` вернул пустой датафрейм по информативному таймфрейму — блок
  `merge_informative_pair` пропускается целиком, колонок `rsi_1h`/`cci_1h` нет;
- в БД бота лежит фильтр с индикатором, которого стратегия не считает (например
  добавили индикатор в `FilterRule`, но не в шаблон — см.
  [how-to](how-to.md#добавить-новый-индикатор), там четыре места не просто так).

⚠️ Ветка `if not conditions` в шаблоне, которая должна была бы вернуть «не входить»,
недостижима: `volume > 0` кладётся в список до неё. Это не мёртвый код «на всякий
случай», это дыра — если чинить, чинить надо туда.

Симптом в проде — резкий рост числа сделок без изменения настроек. Проверяется
`docker logs <c> | grep "не найдена"`.

### Async-метод без `await` — это 500, а не предупреждение

Обе прокси-ручки в [routers/bots.py](../../backend/src/routers/bots.py) возвращали
результат `BotService.get_logs(...)` / `BotService.freqtrade_status(...)` **без
`await`**, хотя обе функции — `async`. Наружу уезжал объект корутины: FastAPI
возвращённую корутину не ждёт, а сразу отдаёт в `jsonable_encoder`, тот падает с
`ValueError: [TypeError("'coroutine' object is not iterable")]`. То есть логи бота из
интерфейса не открывались вообще.

✅ Починено (`await` в обе ручки) и закрыто тестами
`tests/unit/test_bots_router_proxy.py`, которые проверяют тип ответа, а не его текст.

Урок на будущее: ни ruff, ни mypy, ни ручной просмотр диффа этого не поймали —
поймал бы только вызов ручки. Каждая новая ручка, зовущая `async`-метод сервиса,
должна иметь хотя бы один тест, который её действительно выполняет.

### Порты кончились — бот падает без внятной ошибки

`allocate_port()` возвращает `None`, когда все 1000 портов диапазона заняты активными
ботами. `None` уезжает в `Bot.api_port` (колонка `NOT NULL`) и в маппинг портов
docker. Отдельной проверки нет, понятного сообщения пользователю — тоже.

### Файлы бота не обновляются

Повторим, потому что это уже дважды сбивало с толку: `config.json` и стратегия
пишутся один раз при создании. Ни перезапуск контейнера, ни правка шаблона на них не
влияют.

### Генерация стратегии — это конкатенация строк

`repr()` от значений подставляется в шаблон и исполняется как Python внутри
контейнера. Сейчас всё, что туда попадает, проходит валидацию `Literal[...]` в
Pydantic-схеме `FilterRule`. **Любое новое поле, которое поедет в шаблон, обязано
быть так же строго провалидировано** — иначе это дыра для исполнения произвольного кода.

## Что здесь ещё не описано

Осознанные пробелы — если дописываете документ, начинать стоит отсюда:

- **Бэктест и гипероптимизация.** Freqtrade умеет и то, и другое, в проекте не
  используется совсем.
- **Тарифы Bybit.** Комиссия выведена из сделок (~0.06% за круг) и сходится с
  публичной сеткой (taker 0.055% / maker 0.02%), но тариф конкретного аккаунта
  не сверялся и в конфиге не задаётся вовсе.
- **Поведение при ликвидации.** `liquidation_buffer: 0.05` задан, но ни один бот до
  ликвидации не доходил — как это выглядит в данных, неизвестно.
- **Статистика на новой трактовке TP/SL.** Все цифры в этом документе сняты с ботов,
  созданных до `5e1efd8`. Как ведут себя боты с TP/SL в движении цены — пока неизвестно.
- **Частичные входы и выходы** (`adjust_trade_position`) — не используются.
- **Защиты freqtrade** (`protections`: пауза после серии убытков) — не настроены.
  Кандидат на будущее: боты входят по 400 раз за трое суток без всякого тормоза.
- **`stoploss_on_exchange_interval`** — как часто freqtrade сверяет стоп на бирже.
- **Что делать с ботом в статусе `error`.** Воркер его останавливает, но
  автоматического перезапуска нет, а из интерфейса такой бот можно только удалить.
- **Обновление настроек живого бота.** Freqtrade умеет `/reload_config`, мы им не
  пользуемся — единственный путь смены настроек сейчас пересоздание.
