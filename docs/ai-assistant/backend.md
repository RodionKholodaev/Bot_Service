## Почему на бэкенде, а не в Next.js

Next.js умеет route handlers, и соблазн положить агента туда есть. Сделано иначе,
по трём причинам:

1. **Ключ AITunnel не должен покидать сервер.** В Next-приложении он оказался бы
   в серверной части фронта — это ещё один процесс, где надо хранить секрет.
2. **Фронт уже проксирует `/api/*` на FastAPI** (`frontend/next.config.ts`), так что
   отдельный эндпоинт бэкенда подключается без единой строчки конфигурации.
3. **Авторизация уже есть.** `get_current_user` работает так же, как во всех
   остальных роутерах — анонимный доступ к платной модели закрыт бесплатно.

## Конфигурация

`backend/src/config.py`, блок «ИИ-ассистент»:

```python
AITUNNEL_API_KEY: str | None = None            # не задан → фича выключена
AITUNNEL_BASE_URL: str = "https://api.aitunnel.ru/v1"
AI_ASSISTANT_MODEL: str = "gpt-4.1-mini"       # обязана уметь tool calling
AI_SEARCH_MODEL: str = "sonar"                 # perplexity sonar
AI_ASSISTANT_TIMEOUT: float = 120.0
```

Ключ опционален намеренно: `Settings` упадёт на старте, если обязательное поле
не задано, а помощник — не критичная часть продукта. Проверка в одном месте:

```python
# services/assistant/service.py
def assistant_enabled() -> bool:
    return bool(settings.AITUNNEL_API_KEY)
```

AITunnel — OpenAI-совместимый агрегатор, поэтому смена модели (или даже провайдера
с таким же API) — это правка `.env`, а не кода.

## Роутер

`backend/src/routers/assistant.py` — два эндпоинта, оба под `get_current_user`.

### `GET /assistant/status`

```json
{"enabled": true, "web_search_available": true}
```

Фронт дёргает его при монтировании страницы и, если `enabled: false`, вообще не
рендерит помощника. Так одна и та же сборка фронта работает и там, где ключ есть,
и там, где его нет.

### `POST /assistant/chat`

Отдаёт `StreamingResponse` с `media_type="text/event-stream"`. Каждое событие —
строка `data: {...}\n\n`:

```python
async def event_stream() -> AsyncIterator[str]:
    async for event in service.stream(request):
        yield f"data: {json.dumps(event, ensure_ascii=False)}\n\n"
```

`ensure_ascii=False` — чтобы русский текст не раздувался в `\uXXXX` (это реальные
деньги на токенах и трафике).

Заголовки:

| Заголовок | Зачем |
|---|---|
| `Cache-Control: no-cache, no-transform` | Чтобы прокси не кэшировали и не пережимали поток |
| `Connection: keep-alive` | Держим соединение до конца ответа |
| `X-Accel-Buffering: no` | Отключает буферизацию nginx, иначе стрим приедет одним куском |

Если ключа нет — `BadRequestError` (доменное исключение проекта, превращается
в `{"detail": "..."}` через `core/exception_handlers.py`).

## Rate limit

`services/assistant/rate_limit.py`. Каждый вызов модели стоит денег, а эндпоинт
закрыт только авторизацией — без лимита один аккаунт крутит платные запросы
сколько угодно.

```python
ASSISTANT_LIMIT_PER_MINUTE = 10
ASSISTANT_LIMIT_PER_DAY = 100
```

Два **скользящих** окна, а не календарных: иначе в полночь лимит обнулялся бы
рывком — ровно тот момент, когда его удобно обходить. Счётчик — обычная таблица
`assistant_requests` (одна строка на запрос), без Redis: бэкенд и так живёт одним
процессом. Тот же приём уже работает в `services/feedback_service.py`.

### Три неочевидных решения

**Проверка стоит в роутере, а не в `stream()`.** Как только `StreamingResponse`
начал отдавать тело, статус ответа уже ушёл клиенту — `raise` из генератора
не превратится в 429, и пользователь получил бы оборванный SSE вместо ошибки.
Поэтому `check_and_register()` вызывается до создания `StreamingResponse`.

**Запрос отмечается ДО обращения к модели.** Если писать после ответа,
параллельные запросы одного пользователя проскочат мимо счётчика, а прерванный
ответ вообще не будет учтён.

**Строка коммитится сразу**, вопреки общей схеме «коммитит `get_db` в конце
запроса». Для стрима «конец запроса» наступает через минуты, и общая схема дала
бы две проблемы: открытая write-транзакция на всё это время блокирует запись
остальным (SQLite пускает одного писателя), а обрыв стрима откатил бы строку —
лимит обходился бы нажатием «Стоп».

### Что видит пользователь

429 с `{"detail": "..."}` через `core/exception_handlers.py`. Тексты для минутного
и суточного окна разные — человек должен понимать, ждать ему минуту или день.
Фронт показывает такую ошибку янтарной плашкой с часами, а не красной с
восклицательным знаком: упереться в лимит — это норма, а не сбой.

### Чего лимит не делает

Не ограничивает регистрацию: N аккаунтов дают N × 100 запросов в сутки. Если это
станет проблемой, ограничивать надо на уровне регистрации.

Счётчик не чистится — таблица растёт на строку с каждого сообщения. При заметном
объёме понадобится периодическая уборка строк старше суток (для лимита они уже
бесполезны).

## Схемы запроса

`backend/src/schemas/assistant.py`.

```python
class AssistantChatRequest(BaseModel):
    messages: list[ChatMessage]   # 1..40, последнее — текущий вопрос
    form: BotFormSnapshot         # снимок формы
    web_search: bool = False      # тумблер в панели
```

**Поля `BotFormSnapshot` намеренно в camelCase** — это дословный снимок `formData`
из `page.tsx`. Благодаря этому предложения возвращаются с теми же именами полей
и применяются на фронте без слоя маппинга. Единственное «лишнее» поле —
`hasApiKeys`: помощник должен знать, есть ли у пользователя ключи биржи, прежде
чем предлагать боевой режим.

Ограничения (`Field(...)`) стоят не для красоты: `messages` до 40 штук и по 8000
символов, `filters` до 30 — это защита от того, что фронт (или кто-то с curl)
пришлёт мегабайт истории, за который заплатите вы.

## `aitunnel.py` — транспорт

Тонкая обёртка над `httpx`. Отдельная SDK не нужна — API OpenAI-совместимый.

| Функция | Зачем |
|---|---|
| `build_client()` | `httpx.AsyncClient` с таймаутом из настроек, один на диалог |
| `complete(...)` | Обычный запрос. Используется веб-поиском |
| `stream_chat_completion(...)` | Стрим, отдаёт уже распарсенные JSON-чанки |
| `AITunnelError` | Единственный тип ошибки наружу — сеть, ключ, лимиты, 5xx |

Разбор SSE от провайдера устойчив к мусору: строки без `data:`, keep-alive,
служебный `[DONE]` и невалидный JSON пропускаются (последний — с `warning` в лог).
Это не паранойя: провайдеры-агрегаторы регулярно подмешивают в поток своё.

```python
async for line in response.aiter_lines():
    if not line or not line.startswith("data:"):
        continue
    data = line[len("data:"):].strip()
    if not data or data == "[DONE]":
        continue
    yield json.loads(data)   # ошибки JSON гасятся выше
```

## `prompt.py` — что модель знает о продукте

**Самый важный файл для качества ответов.** Здесь единственное место, где описаны
правила продукта для модели.

### `SYSTEM_PROMPT`

Содержит:

- кто аудитория («не программисты и часто не трейдеры») и требование отвечать
  по-русски, коротко, без жаргона;
- полное описание всех четырёх шагов мастера и **всех** полей — включая допустимые
  диапазоны (плечо x1–x20, шаг ползунка сделки, только rsi/cci, шесть таймфреймов);
- смысл индикаторов (RSI < 30 — перепроданность и т.д.) и правило направления:
  для long условия «меньше», для short — «больше»;
- что условия соединяются через **И**, поэтому чем их больше, тем реже сделки;
- **список того, чего в продукте нет** — других индикаторов, бирж, DCA, усреднения,
  мультипар. Это ключевой абзац: без него модель охотно предлагает MACD и Binance
  Spot, а пользователь потом ищет их в форме;
- требование вызывать `suggest_settings` вместо перечисления чисел текстом;
- запрет обещать прибыль и давать инвестиционные советы.

### `render_form_context(form)`

Собирает снимок формы в компактный текст и отдаёт **отдельным** system-сообщением:

```
Текущее состояние формы (то, что пользователь видит прямо сейчас):
- Открыт: Шаг 2 — Пара и плечо
- Режим: Dry Run (симуляция)
- Пара: BTC/USDT
- Плечо: x10
- Условия входа: пусто (бот не сможет открыть ни одной сделки)
...
```

Два отдельных system-сообщения вместо одного склеенного — сознательно: правила
неизменны и хорошо кэшируются провайдером, а снимок формы меняется каждый запрос.

Обратите внимание на формулировки: «пусто (бот не сможет открыть ни одной сделки)»
вместо «filters: []». Модели проще рассуждать над осмысленным текстом, чем над
дампом структуры.

### `build_messages(form, history)`

```
[ system: правила ] + [ system: снимок формы ] + [ вся история диалога ]
```

## `tools.py` — инструменты

Два инструмента, схемы в формате OpenAI. Какие из них уйдут модели, решает
`build_tools(web_search_enabled)` — `web_search` отдаётся, только если пользователь
включил тумблер в панели.

### `suggest_settings`

Ничего не выполняет. Модель им «говорит»: вот значения для формы. Аргументы —
массив `{field, value, reason}`, до 8 штук. `field` ограничен enum'ом
`SUGGESTABLE_FIELDS`, так что модель физически видит только разрешённые имена.

Результат уходит на фронт событием `suggestions`, а модели возвращается короткая
инструкция «предложения показаны, теперь коротко объясни выбор» — иначе она
пытается пересказать те же числа текстом, и пользователь читает одно и то же дважды.

### `web_search`

Вызывает `AI_SEARCH_MODEL` (по умолчанию perplexity `sonar`) обычным
нестриминговым запросом. Sonar сам ходит в интернет и возвращает ответ, а ссылки
кладёт в поле `citations` рядом с `choices` — оттуда мы их и достаём (до 6 штук).

```python
async def run_web_search(client, query) -> tuple[str, list[str]]:
    ...
    return content, sources   # текст для модели, ссылки для пользователя
```

Отдельного поискового API и ключа не нужно: всё идёт через тот же AITunnel.

## Валидация предложений

`normalize_suggestions(raw_arguments)` — **граница доверия**. Всё, что модель
предлагает подставить в форму пользователя, проходит здесь.

Общие правила: не больше 8 предложений, неизвестное поле выбрасывается, при
дубликате поля побеждает первое упоминание, битый JSON даёт пустой список
(не исключение — модели свойственно обрывать аргументы на полуслове).

Правила по полям (`_normalize_value`):

| Поле | Проверка | Результат |
|---|---|---|
| `dryRun`, `useStopLoss` | `bool` или строки `"true"`/`"false"` | `bool` |
| `leverage` | число 1–20 | строка целого (`"3"`) |
| `balanceRatio` | число 5–100 | **округляется к шагу 5** — ползунок ходит только так |
| `stakeAmount` | число > 0 | строка |
| `takeProfit`, `stopLoss` | число 0 < x ≤ 100 | строка без хвостовых нулей |
| `tradingPair` | содержит `/`, длина 5–30 | верхний регистр |
| `algorithm` | `long` \| `short` | как есть |
| `strategyPreset` | `conservative` \| `moderate` \| `aggressive` \| `custom` | как есть |
| `botName` | непустая строка | обрезается до 100 символов |
| `filters` | до 12 правил; в каждом `indicator ∈ {rsi, cci}`, `timeframe` из шести, `condition ∈ {less, greater}`, `value` — число | список валидных правил; **если не выжило ни одного — поле отбрасывается целиком** |

Почему числа возвращаются **строками**: `formData` на фронте хранит их строками —
это значения обычных `<input>`. Так применение предложения не требует приведения
типов и не ломает управляемые инпуты.

Почему пустой список фильтров отбрасывается: бот с нулём условий входа никогда не
откроет сделку, а форма покажет пустой список без объяснений. Лучше не предложить
ничего, чем предложить нерабочее.

Каждое отброшенное предложение пишется в лог на уровне `info` с именем поля и
обрезанным значением — по этим записям видно, что модель систематически путает.

## `service.py` — агентный цикл

`AssistantService.stream(request)` — асинхронный генератор событий. Один вызов =
один ответ пользователю, внутри может быть до `MAX_TOOL_ROUNDS` (3) обращений
к модели.

```
for round in range(MAX_TOOL_ROUNDS):
    ├ отдать status: thinking
    ├ _stream_round() — стримить ответ модели,
    │   текст отдавать наружу событиями delta,
    │   вызовы инструментов копить в sink
    ├ инструментов нет → выйти из цикла (ответ готов)
    ├ это последний раунд → выйти (защита от зацикливания, warning в лог)
    ├ дописать ход ассистента в messages
    └ выполнить каждый инструмент, дописать результат как {"role": "tool", ...}
отдать done
```

### Склейка стриминговых tool calls

Тонкое место. В стриме аргументы инструмента приходят **по кускам**, и склеивать
их надо по `index`, а не по `id` (в первом чанке есть `id`, в последующих — нет):

```python
for call in delta.get("tool_calls") or []:
    index = call.get("index", 0)
    slot = sink["tool_calls"].setdefault(index, {"id": "", "name": "", "arguments": ""})
    if call.get("id"):
        slot["id"] = call["id"]
    function = call.get("function") or {}
    if function.get("name"):
        slot["name"] = function["name"]
    if function.get("arguments"):
        slot["arguments"] += function["arguments"]
```

То есть `{"que` + `ry": "курс BTC"}` в двух чанках превращается в валидный JSON
только после склейки. Если модель зовёт два инструмента сразу — у них разные
`index`, и они собираются параллельно.

### Почему лимит раундов именно 3

Типичный полный сценарий укладывается ровно в три: `web_search` → `suggest_settings`
→ финальный текст. Больше — почти всегда признак того, что модель зациклилась;
меньше — обрежет нормальный сценарий с поиском. При достижении лимита пишется
`warning` и цикл завершается тем, что уже успело накопиться.

### Почему `messages` мутируется на месте

`_run_tool()` принимает список `messages` и дописывает в него результат. Это
сознательное упрощение: диалог с моделью — линейная лента, и передавать её
туда-обратно по значению было бы шумно. Взамен есть жёсткое правило: **никто,
кроме `_run_tool` и самого цикла, в `messages` не пишет**.

## События

Формат наружу — обычные `dict`, роутер лишь заворачивает их в SSE.

```python
{"type": "status",      "stage": "thinking" | "searching", "query": str}
{"type": "delta",       "text": "кусок ответа"}
{"type": "suggestions", "items": [{"field", "value", "reason"}, ...]}
{"type": "sources",     "items": ["https://...", ...]}
{"type": "error",       "message": "текст для пользователя"}
{"type": "done"}
```

`done` отдаётся **всегда**, в том числе после ошибки — фронт по нему снимает
индикаторы, и без него панель зависнет в состоянии «печатает».

## Обработка ошибок

Весь цикл обёрнут в два `except`:

| Что ловим | Что в логе | Что видит пользователь |
|---|---|---|
| `AITunnelError` (сеть, 4xx/5xx провайдера, таймаут) | `logger.exception` | «Не удалось получить ответ от ИИ. Попробуйте ещё раз.» |
| Любое другое исключение | `logger.exception` | «Внутренняя ошибка ассистента.» |

Отдельно: падение **веб-поиска** не роняет весь ответ. Модели дописывается
`"Поиск недоступен. Ответь по своим знаниям и предупреди об этом."` — и она
продолжает нормально, честно предупредив пользователя.

Соблюдается конвенция проекта: логи по-английски, пользовательский текст по-русски,
`logger.critical` не используется (см. [README.md](README.md#логи)).

## Тесты

`backend/tests/unit/test_assistant_suggestions.py` — 8 тестов на
`normalize_suggestions`. Без сети и без БД: это чистая функция от JSON-строки.

`backend/tests/unit/test_assistant_rate_limit.py` — 6 тестов на
`AssistantRateLimiter`, тоже без БД: лимитеру подсовывается
`FakeAssistantRequestRepo` с заданными счётчиками. Закреплено, в частности, что
отбитый лимитом запрос **не** записывается (иначе пользователь сам себе продлевал
бы блокировку) и что окна скользящие. Мутационно проверено: 7 мутаций, все пойманы.

Покрыто: нормальный проход и приведение к строкам, выход за диапазон, привязка
`balanceRatio` к шагу 5, неизвестное поле, отсев неподдерживаемых индикаторов
и таймфреймов внутри `filters`, полный отброс `filters`, дубликат поля, битый JSON.

```bash
cd backend
python -m pytest tests/unit/test_assistant_suggestions.py -v
```

Агентный цикл и транспорт тестами не покрыты — там всё интересное происходит
в разговоре с внешним сервисом. Как прогнать цикл на подменённом провайдере,
если будете его править, — в [how-to.md](how-to.md#прогнать-агентный-цикл-без-реальных-запросов).
